## 0. ★ 串起来：每个工具都在补上一个的漏洞 ✍️

整节课只在回答一个问题：**Alice 怎么把一样东西安全地交给一个可能从没见过的 Bob？** 每出现一个新工具，都是因为上一个工具有解决不了的问题：

```
① 对称加密（AES）                   同一把钥匙锁、同一把钥匙开；快
      ↓ 问题：钥匙怎么安全地交给对方？人一多钥匙数量爆炸；分不清是谁发的
② 非对称加密（RSA / ECC）           公钥公开、私钥自己留；不用事先交换钥匙
      ↓ 问题：只解决了「看不懂」，没解决「有没有被改」；而且很慢
③ Hash（MD5 / SHA-2）               给内容算一个指纹，改一个字指纹全变
      ↓ 问题：Hash 没有密钥，中间人改了内容可以重算一个新指纹
④ 数字签名（私钥签摘要）            只有 Alice 签得出来 → 发现篡改 + 证明是谁 + 不可抵赖
      ↓ 问题：Bob 怎么知道这把公钥真的是 Alice 的？攻击者可以拿自己的密钥对冒充
⑤ 数字证书 + CA = PKI               受信任的第三方背书「这把公钥属于 Alice」
      ↓ 问题：非对称太慢，不能整个会话都用
⑥ Hybrid（TLS / PGP）               非对称验证身份、交换 session key，之后全部用对称
```

之后两个「应用 + 风险」：**Blockchain** 是把 ③ 哈希链 + ④ 签名 + 分布式账本组合起来的业务案例；**风险与量子计算** 说明再好的算法，也会因为密钥管理不善或算法过时而失效。

**一个贯穿全课的类比：寄箱子**

| 工具 | 类比 |
|---|---|
| 对称加密 | 一把钥匙配两份，你一份我一份——但第一次怎么把钥匙交给对方？ |
| 非对称加密 | 你寄给我一把**打开的挂锁**（公钥），谁都能把箱子锁上，只有我有开锁的钥匙（私钥） |
| Hash | 给箱子里的东西拍一张照片——谁都能重新拍一张假照片 |
| 数字签名 | 在照片上盖**只有你才有的印章** |
| 数字证书 / CA | 去公证处证明「这个印章真的是你的」 |
| Hybrid | 先用挂锁寄过去一把钥匙，之后大家都用这把钥匙开保险箱 |

| 工具 | 解决了什么 | 留下什么问题 | 做到哪个目标（p.29） |
|---|---|---|---|
| 对称 | 快速加密大量数据 | 密钥分发、不可扩展、无不可抵赖 | C |
| 非对称 | 不用事先交换密钥 | 慢；没管完整性 | C（+ 密钥分发） |
| Hash | 发现内容被改 | 没有密钥，可被重算 | I（脆弱） |
| 数字签名 | 只有私钥持有人签得出 | 公钥属于谁？ | I + A + N |
| 证书 / CA | 公钥和身份绑定 | 要管理生命周期（吊销） | A（身份信任） |
| Hybrid | 又快又安全 | 密钥管理仍是关键 | C + I + A |

<L4SortQuiz set="why" />

<Callout type="warn" title="三个最容易混的地方">

1. **「Private-key encryption」是对称加密的别名**（p.9），不是「用私钥加密」。非对称的别名是 public-key encryption。
2. **「用私钥加密摘要」= 签名，不是保密**：谁都有公钥，谁都能解开，所以它证明的是「谁签的」，不是「谁能读」。要保密，用的是**收件人的公钥**。
3. **Hash 不是加密**：没有密钥、不可逆、输出长度固定。加密是可逆的（有钥匙就能解回原文）。

</Callout>

## 1. 🟡 加密基础（p.3–8）📝🔍

<Figure src="images/page_06.png" caption="Vigenère Square：SACK GAUL SPARE NO ONE + 密钥 ITALY → ATCVEINLDNIKEYMWGE" source="Slide 6" />

**课件原文**

- Cryptography: **algorithm / formula to protect data**；最早的例子 **Scytale（公元前 487 年）**
- Encryption: **process of converting a message into a form that is unreadable to unauthorized people**；Plaintext → Ciphertext（加密）、Ciphertext → Plaintext（解密），两边都要 key
- **Substitution Cipher**：Vigenère Square（26×26 字母表，用户定义的 encryption key 决定用哪一行）
- **Transposition**（block cipher）：keep a message secret from unintended audiences；Caesar block：fit the text to a number square（e.g. 5 by 5）

**需要理解**

- **加密 = 算法 + 密钥**。Scytale：缠绕书写的规则是算法，木棍的粗细是密钥。算法通常是公开的（AES、RSA 全世界都知道怎么算），**秘密全在密钥里**——所以 p.36 说 *key more important*。
- **Substitution 换「字母是什么」，Transposition 换「字母在哪里」**。
  - Vigenère（课件例子）：每个字母按密钥字母右移。S + I(8) = A，A + T(19) = T，C + A(0) = C，K + L(11) = V……密钥 ITALY 不够长就重复。
  - Caesar block（课件例子）：空格写成 _，把 SACK_GAUL_SPARE_NO_ONE 竖着填进 5×5 方阵，再横着读 → SGS_NAAPNECUAO_KLR____EO。字母一个没变，只换了位置。

<CipherLab />

<Callout type="extra" title="古典密码为什么不安全（课件没讲）">

字母频率是藏不住的：英文里 E 最多，换字母之后「出现最多的那个字母」大概率就是 E；换位置之后字母本身都还在。现代算法（AES、RSA）基于数学难题，密钥空间大到暴力试不完，这些弱点才被堵上。

</Callout>

<MCQ q="（课件原题）Which term describes the information used in conjunction with an algorithm to create the ciphertext from the plaintext?" a="Cipher" b="Code" c="Clear text" d="Key" answer="D">
*EN:* Encryption = algorithm + **key**; the key is the information used with the algorithm to turn plaintext into ciphertext.

加密 = 算法 + 密钥。
</MCQ>

## 2. 🔴 对称加密 Symmetric Encryption（p.9–11、p.15）📝✍️

<Figure src="images/page_10.png" caption="Figure 10-5：Rachel 生成一把 secret key，要用 out of band（另找渠道，图上是 private courier）交给 Alex，双方用同一把钥匙加解密" source="Slide 10" />

**课件原文**

> - **Same 'secret' key** is used both to encrypt and decrypt the message, also known as **private-key encryption**.
> - Can be programmed into **fast** computing algorithms. Used for **bulk data encryption**: databases, files, network traffic.
> - Both sender and receiver **must possess the same secret key**.
> - If either copy of the key is compromised, an intermediate can decrypt and read messages **without sender / receiver knowledge**.

标准算法 **AES**：金融（交易、账户、支付数据，**PCI DSS** 合规）、加密钱包私钥和助记词、**HTTPS / TLS（after secret key exchange）**、WPA2 / WPA3（192 / 256-bit AES）。

p.15「Systemic Key Cryptography」：
- Number of keys for n parties：**n(n−1)/2**
- Advantage：**simple, fast (1,000–10,000× faster than asymmetric)**；theoretically strong if key is secured
- Disadvantage：**key distribution is a major problem**；**not scalable for larger groups**；**key must be regenerated often**；**does not implement nonrepudiation**

**需要理解：类比「一把钥匙配两份」**

你和朋友各拿一份同样的钥匙，用同一个保险箱传东西。好用、开锁快，但有四个麻烦，正好是课件的四个缺点：

| 缺点 | 具体是什么 | 例子 |
|---|---|---|
| **Key distribution** | 第一次怎么把钥匙交给对方？在网上发 → 可能被截获；要安全地发，又需要一条安全通道——先有鸡还是先有蛋 | 图上 Rachel 只能找 private courier 送钥匙（out of band） |
| **Not scalable** | 每两个人要一把单独的钥匙 | 10 人 45 把，100 人 4,950 把，1,000 人 499,500 把（见下面的计算器） |
| **Regenerated often** | 用久了被破解或泄露的风险变大，要常换；每换一次又要重新分发 | 每次换钥匙都要再找一次快递员 |
| **No nonrepudiation** | 两个人拿的是同一把钥匙，谁都能「冒充」对方写一条 | Alex 收到一条转账指令，Rachel 可以说「这是你自己用钥匙伪造的」 |

还有课件第 4 点：**钥匙一旦被偷，对方能在你们完全不知情的情况下读所有消息**——没有任何告警。

<KeyCountLab />

<Callout type="warn" title="命名陷阱">

「Private-key encryption」= 对称加密的别名，因为那把钥匙是两人「私下共享」的。和非对称里的 private key（只有一个人有）是两回事。选择题里 *private-key encryption*、*symmetric encryption*、*AES* 是同一类。

</Callout>

<QA q="（A2 原题 / A2 question）List 3 challenges with symmetric cryptography.（9 marks）">

**English**

1. **Key distribution** — the same secret key must be delivered to the other party through a secure channel before communication; if it is intercepted, all messages can be read.
2. **Not scalable** — n parties need n(n−1)/2 keys, which is hard to manage for large groups, and keys must be regenerated often.
3. **No nonrepudiation** — both parties hold the same key, so neither can prove who sent a message; it cannot support accountable transactions.

**中文解析**

① **密钥分发**：通信前必须通过安全渠道把同一把密钥交给对方，密钥在传递中被截获就全部失效；② **不可扩展**：n 方两两通信需要 n(n−1)/2 把密钥，大群体难以管理，且密钥要经常更换；③ **没有不可抵赖**：双方持有同一把密钥，无法证明某条消息是谁发的，不能用于需要追责的交易。

</QA>

## 3. 🔴 非对称加密 Asymmetric Encryption（p.12–14、p.16，PKI p.14）📝🔍

<Figure src="images/page_13.png" caption="Figure 10-6：Rachel 把公钥放进 public key repository；Alex 用 Rachel 的公钥加密，只有 Rachel 的私钥能解" source="Slide 13" />

**课件原文**

> - Involves **two different keys** (public key and private key), also known as **public-key encryption**.
> - **Either key can be used to encrypt** a message, but then **the other key is required to decrypt** it. If Key A encrypts, only Key B can decrypt.
> - Greatest value when one key serves as **private key** and the other as **public key**. Public keys are freely shared; private key is kept secret.

PKI 专题 p.14 的 Benefits：**easier key management and distribution**；**the private key is never distributed**, therefore more secure；**scalable**。Weakness：**slow to generate fresh strong keys**；**slow to encrypt**。RSA（1977）：no published methods to defeat the system if a **large enough key** is used。

常见算法：**RSA**、**Diffie-Hellman**、**ECC**。用途（Protect data in motion）：**Secure web traffic**（TLS 握手用 RSA 等验证服务器身份、协商临时共享密钥）；**Remote access (SSH)**（ECDH）。

**需要理解：类比「打开的挂锁」**

Bob 做了很多把一样的**挂锁**，打开着到处送人（公钥），开锁的钥匙只有他自己有（私钥）。谁想给 Bob 寄东西，就拿一把挂锁「咔」地锁上箱子——锁上以后连寄件人自己都打不开，只有 Bob 能开。

- 它一次解决了对称的两个问题：**不用事先交换钥匙**（挂锁本来就可以公开发）；**可扩展**（n 个人只要 n 对，见上面计算器）。
- 代价：**慢**，比对称慢 1,000–10,000 倍，所以不拿来加密大量数据（→ §7 Hybrid）。

<Figure src="images/page_14.png" caption="p.14：Alice 用 Bob 的公钥加密，Bob 用 Bob 的私钥解密" source="Slide 14" />

<QA q="（课件原题 p.14）Sender use which key? How about receiver?">

**答案**：图上的场景是保密通信——**Sender（Alice）用 Bob's Public Key 加密，Receiver（Bob）用 Bob's Private Key 解密**。图上另外两把（Alice's Private Key、Alice's Public Key）是干扰项：它们用在 Alice 要**签名**的时候（Alice 私钥签，Bob 用 Alice 公钥验）。

*EN:* For confidentiality the sender encrypts with the **receiver's public key** and the receiver decrypts with **its own private key**. Alice's key pair would be used only if she wanted to sign the message.

</QA>

**哪把钥匙干什么（最常考）**

| 目的 | 发送方 Alice 用 | 接收方 Bob 用 | 口诀 |
|---|---|---|---|
| **保密**（只有 Bob 能读） | **Bob 的公钥**加密 | **Bob 的私钥**解密 | 用**收件人**的钥匙 |
| **签名**（证明是 Alice 发的） | **Alice 的私钥**签 | **Alice 的公钥**验证 | 用**发件人**的钥匙 |

记法：**私钥永远只在主人自己手上用**——要么解密寄给自己的东西，要么签自己发出去的东西。

<L4SortQuiz set="key" />

| 对比 | Symmetric | Asymmetric |
|---|---|---|
| 钥匙 | 1 把共享 | 每人 1 对（公钥 + 私钥） |
| n 人需要 | n(n−1)/2 | 2n |
| 速度 | 快 | 慢 1,000–10,000 倍 |
| 密钥分发 | 难（最大痛点） | 容易：公钥公开，私钥从不传送 |
| 不可抵赖 | 不支持 | 支持（配合签名） |
| 算法 | AES | RSA、Diffie-Hellman、ECC |
| 典型用途 | 加密大量数据（数据库、文件、TLS 传输阶段） | 交换密钥、验证身份、签名 |

<QA q="（课件原题 p.18 Class Discussion）What is the fundamental difference between symmetric and asymmetric encryption?">

**English**

Symmetric encryption uses **one shared secret key** for both encryption and decryption; asymmetric encryption uses **a mathematically related key pair** — a public key that is freely shared and a private key kept secret — where what one key encrypts only the other can decrypt.

**中文解析**

根本区别在**钥匙的数量和归属**：对称是双方**共用同一把**秘密钥匙；非对称是**每人一对**、数学相关的钥匙，公钥公开、私钥只有自己有，一把加密只有另一把能解。其他差别（速度、密钥分发、不可抵赖）都是从这一点推出来的。

</QA>

<QA q="（课件原题 p.18 Class Discussion）What is the limitation of symmetric encryption?">

**English**

**Key distribution** is the fundamental limitation: the shared key must reach the other party through a secure channel before any secure communication can start. It also does not scale (n(n−1)/2 keys for n parties), keys must be regenerated often, and it cannot provide nonrepudiation because both parties hold the same key.

**中文解析**

最根本的局限是**密钥分发**：开始加密通信之前，必须先找一条安全渠道把同一把钥匙交给对方。另外还有：不可扩展（n 人要 n(n−1)/2 把）、要经常换钥匙、没有不可抵赖（双方拿同一把钥匙，分不清是谁发的）。

</QA>

<Callout type="extra" title="为什么从公钥推不出私钥（课件没讲）">

非对称基于「一个方向好算、反方向极难」的数学问题。RSA 的例子：两个大质数相乘很容易，把乘积分解回那两个质数极难——足够大的密钥，今天的计算机要算成千上万年（p.37）。这也是量子计算威胁它的原因（§11）。

</Callout>

<MCQ q="（课件原题）What term describes a cryptographic method that incorporates mathematical operations involving both a public key and a private key to encipher or decipher a message?" a="Private-key encryption" b="Symmetric encryption" c="Advanced Encryption Standard (AES)" d="Asymmetric encryption" answer="D">
*EN:* Using both a public and a private key is the definition of **asymmetric** encryption; A, B and C all describe symmetric encryption.

A、B、C 都是对称加密的说法或算法。
</MCQ>

<QA q="（A2 原题 / A2 question）Explain, with a brief example, the difference between symmetric and asymmetric encryption.（6 marks）">

**English**

**Symmetric encryption** uses the **same secret key** to encrypt and decrypt. It is fast and suits bulk data, but both parties must share the key first. *Example*: a company encrypts its database with AES, and every authorised system holds the same key.
**Asymmetric encryption** uses a **mathematically related public / private key pair**: what one key encrypts, only the other can decrypt. The public key is shared freely and the private key is kept secret, which solves key distribution and enables digital signatures, but it is slow. *Example*: a customer encrypts data with the bank's public key from its certificate, and only the bank's private key can decrypt it.

**中文解析**

对称：加密和解密用**同一把**密钥，快，适合大量数据，但双方要先共享密钥。例：公司用 AES 加密数据库，所有授权系统持有同一把密钥。非对称：用一对**数学相关的公钥和私钥**，一把加密只有另一把能解，公钥公开、私钥自己保存，解决了密钥分发并支持签名，但慢。例：客户用银行网站证书里的公钥加密，只有银行的私钥能解开。

</QA>

## 4. 🔴 哈希 Hashing（p.19–23）📝🔍

<Figure src="images/page_21.png" caption="任意文件（光盘、邮件、密码）经过 Hash Algorithm（MD5、SHA-1、SHA-2）→ 固定长度的 Hash Value / Message Digest；用途：Protect Password、Message Digest；不能反推（红叉）" source="Slide 21" />

**课件原文**

> Hash functions are mathematical algorithms used to **confirm the identity of a specific message** and **confirm that the content has not been changed**. It generates a **hash value or message digest**. Convert **variable-length** messages into a single **fixed-length** value.

特性（p.22）：**one-way, irreversible**；**same data → same hash value**；**small change → big change in hash value**；**uniqueness**（impossible to find two messages with the same hash value — **hash collision**）
用途（p.23）：**password storage & protection**；**data integrity verification（message digest）**；**digital signatures**（via public key cryptography & hashing functions）

**需要理解：类比「指纹」和「榨汁」**

- 像**指纹**：一个人对应一个固定的指纹，看指纹能认出是不是同一个人；但从指纹变不回一个人。
- 像**榨汁**：苹果榨成汁很容易，汁变不回苹果（one-way）；同样的苹果榨出同样的汁（same data → same hash）。

| 特性 | 意思 | 为什么重要 |
|---|---|---|
| One-way | 只能从消息算哈希，不能反推 | 数据库里存密码哈希，被偷也拿不到原密码 |
| Same data → same hash | 同样输入永远同样输出 | Bob 重算一遍就能比对 |
| Small change → big change | 改一个字，哈希大约一半的位都变 | 看不出「只差一点」，篡改无处可藏 |
| Uniqueness | 找不到两条不同消息哈希相同 | 不然攻击者能换成另一条哈希相同的假消息 |
| Fixed length | 一本书和一个字的哈希一样长（SHA-256 永远 256 位） | 方便比对和签名 |

<HashLab />

| | 加密 | Hash |
|---|---|---|
| 要不要密钥 | 要 | **不要**（课件原题） |
| 能不能还原 | 有钥匙就能解回原文 | **不能**，单向 |
| 输出长度 | 随原文变长 | **固定** |
| 目的 | 机密性（C） | 完整性（I） |

**三个用途怎么用**

1. **存密码**：只存哈希。登录时把输入的密码再算一次哈希，和存的比对。还要**加盐**（每个用户加一段随机值再哈希，L2），否则常见密码的哈希人人都查得到——PKI 课件图里的摘要 `e10adc3949ba59abbe56e057f20f883e` 其实就是密码「123456」的 MD5，网上一搜就能查到。
2. **检查完整性**：下载软件时官网公布一个 SHA-256 值，自己算一遍对得上就说明文件没坏、没被换。
3. **数字签名**：先对消息做哈希得到摘要，再签摘要（§5）。

<Callout type="warn" title="Hash 最大的弱点：谁都能算">

因为**没有密钥**，任何人用同样算法、同样输入都能算出同样结果。所以攻击者改了内容可以**重新算一个新哈希**一起发过去，Bob 比对照样通过——这就是 §5 Step ① 的问题，也是需要数字签名的原因。

</Callout>

<Callout type="extra" title="MD5 和 SHA-1 已经不安全（了解即可）">

课件图里的 MD5、SHA-1 已经被找到碰撞（两份不同的文件哈希相同），违反了 uniqueness，不能再用于签名或证书；现在用 SHA-256（属于 SHA-2）。这也是 §10「cryptographic algorithm obsolescence」的例子。

</Callout>

<MCQ q="（课件原题）True or False: Hashing functions require the use of keys?" a="True" b="False" answer="B">
*EN:* **False** — hash functions use no key, which is why a hash alone cannot prove who sent a message.

不需要密钥。
</MCQ>

## 5. 🔴 Hash → 数字签名 → 数字证书（PKI 专题 p.15–22）📝✍️

这是全课设计最精心的部分：同一张图加了三次东西，每次补上一个漏洞。先用下面的组件自己扮演攻击者试一遍：

<PkiTrustLab />

| | 做法 | 攻击者能做什么 | 做到了 | 新问题 |
|---|---|---|---|---|
| ① 只用 Hash | 消息 + 哈希一起发，Bob 重算比对 | 改内容、**重算哈希**，Bob 照样通过 | 脆弱的 I | 没有密钥 |
| ② + 数字签名 | 用 **Alice 私钥**签摘要；Bob 用 Alice 公钥验 | 改内容后签不出对得上的签名 → 被发现；但可以拿**自己的密钥对冒充 Alice** | I + A + N | 公钥属于谁？ |
| ③ + 数字证书 | CA 签发证书，背书「这把公钥是 Alice 的」 | 拿不到受信任 CA 签发的「Alice」证书 → 冒充被拒 | 再加身份信任 | 要管理证书生命周期 |
| 三步都**没有** | — | — | **C**：签名不加密消息本身 | 要保密还得加密 → Hybrid |

<Callout type="warn" title="表里的 A 是 Authentication，不是 Availability">

这里用的是 p.29 **密码学的四个目标**（C / I / **A**uthentication / N），不是 L1 的 CIA 三元组。数字签名证明的是「发送方是谁」= Authentication；PKI p.16 原话是 *integrity and **authenticity** of the sender*。密码学工具本来就不负责 Availability（证书过期、钥匙丢了反而会让系统用不了）。

| 出现的地方 | A 代表 |
|---|---|
| L1 CIA 三元组 | **Availability** |
| L3 VPN 要做到的 CIA（p.29） | **Authentication** |
| L4 密码学四个目标（p.29） | **Authentication** |

判断方法：讲密码学工具或 VPN 时，A 是 Authentication；讲信息安全总体目标时，A 是 Availability。

</Callout>

### 5.1 Step ①：只用 Hash

<Figure src="images/pki_02.png" caption="Alice 把消息和哈希一起发给 Bob，Bob 重算比对" source="PKI p.15" />

**课件原题（PKI p.15）**

> **Q1：** Does this process ensure confidentiality and integrity?
> **课件答案：** only integrity
>
> **Q2：** Subject to what types of attack?
> **课件答案：** sniffing, spoofing, and man in the middle

**需要理解**：消息是明文（被 sniffing 看光，没有 C）；中间人截获后改内容、重算哈希再发给 Bob（MITM），Bob 比对仍然一致；攻击者还可以直接冒充 Alice 发一条全新的消息（spoofing）。所以只是**脆弱的完整性**。

### 5.2 Step ②：加上数字签名

<Figure src="images/pki_04.png" caption="PKI with Digital Signature：Alice 用红色私钥把摘要锁成 Digital Signature；Bob 用 Alice 的蓝色公钥解开，和自己重算的摘要 Compare" source="PKI p.16–17" />

**课件原题（PKI p.16）**

> **Q：** Does this process now ensure confidentiality, integrity, and authenticity?
> **课件答案：** Only ensures integrity and authenticity of the sender.

**需要理解：逐步拆开**

```
Alice：消息 ──Hash──► 摘要 ──用 Alice 私钥加密──► 签名；把「消息 + 签名」发出去
Bob：  签名 ──用 Alice 公钥解开──► 摘要 A
       消息 ──自己 Hash──────────► 摘要 B
       A = B → ✓ 没被改，而且是 Alice 签的；A ≠ B → ✗
```

- 攻击者改了消息，摘要 B 就变了；他想配一个新签名，必须有 **Alice 的私钥**——没有 → 篡改被发现（**Integrity**）。
- 能用 Alice 的公钥解开 → 一定是 Alice 的私钥签的（**Authenticity**）→ Alice 事后赖不掉（**Nonrepudiation**）。
- **为什么签摘要而不签整条消息？** 非对称很慢，摘要固定又短（几十个字节），签它快得多；而摘要和消息一一对应，签摘要等于签了消息。
- 仍然**没有机密性**：消息本身是明文发出去的。
- **新问题**：Bob 手上的「Alice 公钥」是哪来的？攻击者可以生成自己的密钥对，签好名，再告诉 Bob「这是 Alice 的公钥」——验证在数学上完全通过，Bob 认错了人。

<Callout type="memo" title="只要是数字签名，就一定是非对称吗？——是（复习时问的）">

要做到 **nonrepudiation**，必须只有签名人自己有那把钥匙 → 只能用非对称的**私钥**。但对称加密也有一个「像签名」的工具：**MAC（Message Authentication Code，如 HMAC）**，要分清：

| | 数字签名 | MAC（HMAC） |
|---|---|---|
| 钥匙 | 发送方**私钥**签，任何人用**公钥**验 | 双方**共享同一把**对称密钥 |
| 做法 | Hash → 用私钥签摘要 | Hash（消息 + 共享密钥） |
| Integrity | ✅ | ✅ |
| Authentication | ✅ | ✅（证明是「有这把钥匙的人」发的） |
| **Nonrepudiation** | ✅ | ❌ |
| 速度 | 慢 | 快 |
| 用在哪 | 电子合同、软件签名、证书、PGP / S/MIME | TLS 传输阶段每条记录的完整性校验 |

MAC 做不到不可抵赖的原因，和对称加密的第四个缺点一样：两个人拿同一把钥匙，Alice 可以说「这条是 Bob 自己算出来的」。

还要注意两点：
- **签名本身还不够**：私钥被偷了，签名人就能说「不是我签的」。所以不可抵赖还要靠私钥保管好，以及证书把公钥和身份绑定（Step ③）。
- **电子签名 ≠ 数字签名**：PDF 上贴一张手写签名的图、打上名字，法律上可能算电子签名，但没用到密码学，谁都能复制。课件讲的 digital signature 指用私钥签。

</Callout>

### 5.3 Step ③：加上数字证书

<Figure src="images/pki_05.png" caption="证书 = User's public key + CA's digital signature + Validation period" source="PKI p.18–19" />

**课件原题（PKI p.18）**

> **Q：** How to ensure the validity of someone's public key?
> **答案：** 用 **digital certificate**——由受信任的第三方 **certificate authority (CA)** 签发，把公钥和持有者身份绑定在一起（就是同一页右边的定义）。

**课件原文**

> A digital certificate is an electronic document that contains **a public key value and identifying information about the entity that controls the key**. Often issued by a third party, i.e., a **certificate authority (CA)**.
> 证书内容：**User's public key · CA's digital signature · Validation period**

主课件 p.25：Digital certificates provide communicating parties with the **assurance that the people they are communicating with truly who they claim to be**; essentially **endorsed copies of individual's public key**. CA 例子：Symantec、IdenTrust、AWS、GlobalSign、Comodo、Entrust、DigiCert。

**需要理解：证书就是「CA 签了名的公钥」**

- CA 核实 Alice 的身份后，把「Alice 的身份 + Alice 的公钥 + 有效期」打包，**用 CA 自己的私钥签名**，这就是证书。
- Bob 收到证书：用 **CA 的公钥**验证这个签名 → 通过就相信「里面的公钥真的属于 Alice」→ 再用这把公钥去验 Alice 的签名。
- 攻击者能自己生成密钥对，但**没法让受信任的 CA 给他签一张写着 Alice 的证书**。他自签的证书，浏览器会直接报「不受信任」。
- 那 CA 的公钥又靠谁证明？→ **证书链（certificate chain）**，一直追到浏览器 / 操作系统**预装**的根 CA（PKI 课堂实操 3：Chrome Root Store）。

<Figure src="images/page_26.png" caption="Figure 10-7：证书的 General / Details / Certification Path 三个标签页——amazon.com 由 DigiCert Global CA G2 签发，链条顶端是 DigiCert Global Root G2" source="Slide 26" />

```
DigiCert Global Root G2      ← 根 CA：预装在浏览器的 Root Store 里，自己给自己签
   └─ DigiCert Global CA G2  ← 中间 CA：由根 CA 签发
        └─ www.amazon.com    ← 网站证书：由中间 CA 签发
```

**PKI 课堂实操（p.20–22）**

<Figure src="images/pki_07.png" caption="In-Class Try Out (1)：看安装包属性里的 Digital Signatures 标签" source="PKI p.20" />

> **课件原题（Try Out 1）：** Download an installation file → right click for its properties → go to the "Digital Signatures" tab — **does all program have this tab?**
> **答案：** **不是**。只有厂商用自己的私钥签过名的程序才有这个标签（点 Details 能看到签名者和证书）。没有这个标签 = 没签名，来源和完整性都无法验证，安装前要更小心。

<Figure src="images/pki_08.png" caption="In-Class Try Out (2)：在 Chrome 查看 amazon.com 的证书" source="PKI p.21" />

**课件原题（Try Out 2）**：Open Chrome and visit www.amazon.com → click on the Secure logo → "Connection is secure" → "Certificate is valid", check the General and Details tabs, and answer:

|---|---|---|
| 1) Which CA issued this digital certificate? | General：Issued by | DigiCert Global CA G2 |
| 2) Who is the root CA for this certificate? | Certification Path 最上面 | DigiCert Global Root G2 |
| 3) What's the validation period of this certificate? | General：Valid from / to | 通常一年左右（每次看到的日期不同） |

- 证书还要能**吊销（revocation）**：私钥泄露、员工离职、网站停用时，CA 宣布这张证书作废，浏览器检查时就会拒绝（§6）。

<QA q="Explain why a digital certificate solves a problem that a digital signature alone cannot.">

**English**

A digital signature only proves that **whoever holds the private key** signed the message; it cannot prove that the matching public key really belongs to the claimed person. An attacker can sign with their own key pair and pass off the public key as Alice's, and verification still succeeds mathematically. A **digital certificate**, signed by a trusted **certificate authority (CA)**, binds the public key to the owner's identity with a validity period. Bob first checks that the certificate chains to a root CA he trusts; an impostor cannot obtain such a certificate, so the impersonation is rejected.

**中文解析**

数字签名只能证明「持有这把私钥的人签了这条消息」，但无法证明对应的公钥真的属于声称的人：攻击者可以用自己的密钥对签名，再谎称那是 Alice 的公钥，验证在数学上照样通过。证书由受信任的第三方 CA 签名，把公钥和身份绑定在一起，并有有效期；Bob 先验证证书链指向自己信任的根 CA，冒充者拿不到这样的证书，就会被拒绝。

</QA>

<QA q="For each step — hash only, + digital signature, + digital certificate — state which security properties are achieved.">

**English**

- **Hash only**: weak integrity — a man-in-the-middle can alter the message and recompute the hash.
- **+ Digital signature**: integrity plus **authenticity of the sender** (and nonrepudiation); still no confidentiality.
- **+ Digital certificate**: also confirms the public key belongs to the claimed identity, preventing impersonation.
Confidentiality additionally requires encryption — in practice a hybrid system.

**中文解析**

只有 Hash：脆弱的完整性（中间人可重算）；+ 数字签名：完整性 + 发送方真实性（以及不可抵赖），仍无机密性；+ 数字证书：在签名基础上确认公钥属于声称的身份，防止冒充。要机密性还需要加密（实际用 hybrid）。

</QA>

## 6. 🔴 PKI 的价值与密码学四个目标（p.27–29）📝✍️

<Figure src="images/page_27.png" caption="Class Discussion（6 minutes）：PKI 给组织带来什么价值；本课的密码工具各自做到什么" source="Slide 27" />

**课件原文（p.28，课堂讨论的答案）**

- **Trust Establishment and Identity Verification**
- **Data Confidentiality and Integrity Protection**
- Typical PKI solution integrates：**A certificate authority (CA)** · **Certificate Enrollment** · **Verification** · **Revocation**

**四个根本目标（p.29）**：**Confidentiality · Integrity · Authentication · Nonrepudiation**（nonrepudiation means customers or partners can be **held accountable for transactions**, such as online purchases, which they **cannot later deny**）

**需要理解**

- **PKI 是什么**：不是某一个算法，而是一整套**基础设施**——CA、证书、注册、验证、吊销的流程和规则，让前面的非对称、哈希、签名能在**互不认识的人之间规模化地使用**。
- 没有 PKI：每两个人都要事先见面确认对方的公钥。有了 PKI：只要信任少数几个根 CA，就能信任全世界几百万个网站。
- 四个环节对应证书的一生：**Enrollment**（申请：CA 核实身份后签发）→ **Verification**（使用：对方检查签名、有效期、域名）→ **Revocation**（作废：私钥泄露或员工离职时宣布无效）。Revocation 最容易漏答。

<QA q="（课件原题 p.27 Class Discussion）What are the cryptographic tools discussed in this module, and what does each accomplish?">

**答案**：五种工具，各自对应四个目标中的一部分（见下表）：对称加密 → 快速保密大量数据；非对称加密 → 保密 + 解决密钥分发；Hash → 完整性；数字签名 → 完整性 + 身份 + 不可抵赖；数字证书 / CA → 确认公钥属于谁。实际部署时组合成 hybrid（TLS）。

*EN:* Symmetric encryption provides fast confidentiality for bulk data; asymmetric encryption provides confidentiality and solves key distribution; hashing provides integrity; digital signatures provide integrity, authentication and nonrepudiation; digital certificates issued by CAs bind public keys to identities. TLS combines them in a hybrid system.

</QA>

<QA q="（课件原题 p.27 Class Discussion）How does public key infrastructure add value to an organisation seeking to use cryptography to protect information assets?（10 marks）">

**English**

1. **Trust establishment and identity verification** — CAs issue certificates binding public keys to identities, so customers know they reach the real bank website and partners can verify who signed a document.
2. **Confidentiality and integrity protection** — certified public keys are used to negotiate session keys securely (TLS), and signatures detect tampering.
3. **Nonrepudiation** — parties cannot later deny e-contracts or online purchases.
4. **Scalability** — no pairwise key exchange is needed; public keys can be published openly.
5. **Manageability** — enrolment, verification and **revocation** manage the certificate lifecycle, e.g. revoking a certificate when a private key leaks or an employee leaves.

**中文解析**

① **建立信任、验证身份**：CA 签发证书，把公钥和身份绑定，客户能确认自己连的是真的银行网站，合作方能确认签名者身份；② **保护机密性和完整性**：证书里的公钥用于安全协商会话密钥（TLS），签名用于检测篡改；③ **不可抵赖**：电子合同、网购交易事后不能否认；④ **可规模化**：不需要两两交换密钥，公钥可以公开发布；⑤ **可管理**：通过注册、验证、吊销管理证书生命周期，私钥泄露或员工离职时能吊销证书。

</QA>

## 7. 🔴 Hybrid Cryptography 与 TLS（p.16–17，PKI p.23–30）📝✍️

<Figure src="images/pki_10.png" caption="Hybrid Cryptography System：先用非对称 + 证书验证 Amazon 的身份，连接建立后双方用同一把对称 session key（黄色钥匙）加密后续所有流量" source="PKI p.23" />

**课件原文**

> **Hybrid Cryptography System**：Asymmetric key algorithm is used **to verify the identity of the owner and its public key**. Once connection is built, **symmetric key (session key)** is used to encrypt and decrypt **all following traffic** between the two parties.
> HTTP does not encrypt the data, making it susceptible to eavesdropping. **HTTPS**: the browser and server establish a **secure channel using TLS/SSL before any actual data** is exchanged.

**需要理解：为什么要「混合」**

| 只用对称 | 只用非对称 | Hybrid |
|---|---|---|
| 快，但第一次的钥匙怎么在公网上交给对方？也验证不了对方是谁 | 能解决分发和身份，但慢 1,000–10,000 倍，传网页、视频扛不住 | 非对称**只做开头那一小段**（验证身份 + 交换钥匙），之后全部交给快的对称 |

类比：先用 Bob 的**挂锁**把一把普通钥匙锁在小盒子里寄过去（慢，但安全）；之后两人都用这把钥匙开保险箱传大件（快）。

<Figure src="images/page_17.png" caption="TLS/SSL Handshake in HTTPS：Client Hello / Server Hello → Certificate（CA）→ Key Exchange（非对称）→ Session Key Established（对称）" source="Slide 17" />

<TlsLab />

| 阶段 | 用什么 | 作用 |
|---|---|---|
| 握手 | **证书 + 非对称**（RSA / ECDH） | 验证服务器身份（证书由 CA 签）；安全地协商出 session key，不怕被窃听 |
| 传输 | **对称**（AES） | 用 session key 加密网页数据，快 |
| 全程 | **哈希 / MAC** | 检查数据在传输中没被改 |

<Figure src="images/pki_13.png" caption="SSL：Client A 和 Server A 每次会话（1st / 2nd / 3rd session）都用一把新的 session key" source="PKI p.27" />

- **Session key 只用一次**：每次连接重新协商。好处是某一把泄露了也只影响那一次会话，攻击者不能拿它解密以前和以后的流量。
- **HTTP vs HTTPS**（PKI p.26）：HTTP 走 80 端口、明文（浏览器显示 *Not secure*）；HTTPS 走 443 端口、有 SSL 证书、加密（显示锁头）。SSL 是 TLS 的前身，现在实际用的都是 TLS，但习惯上还叫「SSL 证书」。

<QA q="（A2 原题 / A2 question）Explain hybrid encryption (3). Why does TLS use both asymmetric and symmetric encryption rather than one type (4)? Include the specific roles each plays in a TLS session (8).">

**English**

**Hybrid encryption**: asymmetric cryptography verifies identities and securely exchanges a temporary symmetric **session key**; all subsequent data is encrypted with that symmetric key.
**Why both**: symmetric encryption is fast but cannot distribute keys securely over a public network or verify identity; asymmetric encryption solves key distribution and authentication but is 1,000–10,000 times slower, unsuitable for bulk data. Combining them gets the strengths of each.
**Roles in a TLS session**:
1. In the handshake the server presents a **CA-signed certificate**; the client verifies it with the CA's public key, authenticating the server.
2. An **asymmetric** algorithm (RSA or ECDH) negotiates the **session key**, which eavesdroppers cannot obtain.
3. All web data is then encrypted with a **symmetric** algorithm (AES) using the session key — fast enough for bulk traffic.
4. Each record carries an **integrity check** (hash-based MAC) to detect tampering.
5. The session key is discarded when the session ends and renegotiated next time.

**中文解析**

**Hybrid**：用非对称加密验证身份并安全交换一把临时的对称会话密钥，之后所有数据用这把对称密钥加密。
**为什么两种都用**：对称快但无法在公共网络上安全分发密钥，也不能验证身份；非对称能解决分发和身份验证，但比对称慢 1,000–10,000 倍，不适合大量数据。组合起来兼得两者的优点。
**TLS 中的角色**：① 握手时服务器发送 CA 签发的证书，客户端用 CA 公钥验证证书，确认服务器身份；② 用非对称算法（RSA 或 ECDH）协商出会话密钥，窃听者拿不到；③ 之后的网页数据都用对称算法（AES）和会话密钥加密，速度快；④ 每条记录附带完整性校验，检测篡改；⑤ 会话结束后会话密钥作废，下次重新协商。

</QA>

**它们都是前面工具的组合，只是用在不同地方**

| 环境 | 协议 | 用了哪些工具 | 保护什么 |
|---|---|---|---|
| Web | SSL → TLS | 证书 + 非对称握手 + 对称 AES + MAC | 浏览器和网站之间传输的数据 |

#### ① SSL / TLS：Web

**解决什么问题**：HTTP 是明文，路上的人能看到密码、能改网页、能冒充网站。TLS 夹在 HTTP 和网络之间：HTTP + TLS = **HTTPS（端口 443）**，一次解决 C（加密）、I（MAC）、A（证书）。

<Figure src="images/pki_12.png" caption="HTTP vs HTTPS：HTTP（80）是 Insecure Connection；HTTPS（443）有 SSL Certificate，是 Encrypted Connection" source="PKI p.26" />

**为什么前身叫 SSL，后来改叫 TLS**

| 年份 | 版本 | 发生了什么 |
|---|---|---|
| 1995 | SSL 2.0 | 网景公司（Netscape，早期浏览器）为网上购物开发。1.0 有缺陷，没公开发布 |
| 1996 | SSL 3.0 | 修了 2.0 的漏洞，大规模使用 |
| 1999 | **TLS 1.0** | 交给国际标准组织 IETF 统一管理，**改名 TLS**，技术上是 SSL 3.0 的改进版 |
| 2006 / 2008 | TLS 1.1 / 1.2 | 修补漏洞，支持更强的算法（SHA-256、AES-GCM） |
| 2018 | TLS 1.3 | 删掉所有不安全的旧算法，握手更快，每次会话强制用新的临时密钥 |

- **改名的原因**：从一家公司的私有技术变成开放的国际标准，换一个中立的名字。
- **TLS 比 SSL 解决了什么**：SSL 本身被攻破了（2014 年 POODLE 攻击破解 SSL 3.0，之后 SSL 全面禁用；TLS 1.0 / 1.1 也在 2020 年前后被淘汰）；淘汰了 MD5、SHA-1、RC4 这些过时算法（§10「算法过时」）；TLS 1.3 下即使服务器私钥以后泄露，以前录下来的会话也解不开。
- **为什么还叫「SSL 证书」**：纯粹是习惯。证书本身（X.509 格式，CA 签发）和用 SSL 还是 TLS 无关。
- 除了网页，TLS 还用在：邮件服务器之间的传输、L3 的 **SSL VPN**、手机 App 和服务器通信、网银 API。

#### ② Email：PGP、S/MIME、PEM

**为什么邮件要单独的协议？TLS 不够吗？** TLS 只保护**一段路**（你的电脑 → 邮件服务器）；邮件在服务器上、中转服务器上是明文存着的。PGP 和 S/MIME 是**端到端**的，从写信人一路加密到收信人。

```
TLS：       你 ══🔒══ 你的邮件服务器（明文存放）══🔒══ 对方服务器（明文存放）══🔒══ 收信人
PGP/S/MIME：你 ═══════════════════ 🔒 整封信一路加密 🔒 ═══════════════════ 收信人
```

<Figure src="images/pki_14.png" caption="PGP：hybrid cryptosystem，免费或低成本，邮件和文件加密的开源标准；签名之后、加密之前用 ZIP 压缩" source="PKI p.28" />

**PGP（Pretty Good Privacy）**：1991 年由 Phil Zimmermann 开发，免费（现在的开源版本叫 OpenPGP / GPG）。发信三步：

```
① 签名：Hash 邮件 → 用发件人私钥签摘要                         （I + A + N）
② 压缩：用 ZIP 压缩「邮件 + 签名」                              （变小，打乱规律）
③ 加密：随机生成一把对称 session key，用它 AES 加密整个包；
        再用收件人的公钥加密这把 session key，一起发出去        （C，这就是 hybrid）
```

收信人反过来：自己的私钥解出 session key → 解密 → 解压 → 用发件人公钥验签名。

- **签名为什么最先**：签的是原始内容，收信人解开后能直接验证原文。**压缩为什么在加密前**：加密后的数据看起来是随机的，几乎压缩不了；压缩还打乱原文规律，让破解更难。
- **怎么信任对方的公钥**：不靠 CA，靠 **web of trust（信任网）**——用户之间互相给对方的公钥签名担保。

**S/MIME（Secure/Multipurpose Internet Mail Extensions）**：功能和 PGP 一样（签名 + hybrid 加密），区别是**靠 CA 签发的证书**信任公钥，内置在 Outlook、Apple Mail，适合企业统一给员工发证书。

**PEM（Privacy-Enhanced Mail）**：1993 年 IETF 最早的邮件加密标准，基本没普及就被 S/MIME 取代；留下来的是**文件格式**——证书、密钥文件常见的 `.pem` 后缀。

| | PGP | S/MIME |
|---|---|---|
| 信任公钥靠 | web of trust（用户互相担保） | CA 签发的证书（PKI） |
| 适合 | 个人、技术社群 | 企业 |
| 成本 | 免费 / 低成本 | 买证书或公司统一发 |

#### ③ Wireless：WEP → WPA → WPA2 → WPA3

无线信号在空气里传播，附近谁都收得到，所以必须加密。这一段主要用**对称加密**：Wi-Fi 密码就是双方共享的钥匙（或用来推算钥匙）。

<Figure src="images/pki_15.png" caption="WEP vs WPA vs WPA2 vs WPA3" source="PKI p.29" />

| | 为什么出现 | 加密 | 问题 |
|---|---|---|---|
| **WEP**（1997） | 第一代，目标是「和有线一样隐私」（Wired Equivalent Privacy） | RC4 | 密钥固定不变、初始化向量太短会重复，几分钟就能破 |
| **WPA**（2003） | **救急方案**：WEP 被破后，旧设备升级固件就能用；每个数据包换一把密钥（TKIP） | TKIP / RC4 | 底层还是 RC4，只是临时补丁 |
| **WPA2**（2004） | 正式标准，换成 **AES**，用了十几年 | AES-CCMP | 2017 年 KRACK 能骗设备重装密钥（打补丁可修）；共享密码的版本怕离线暴力猜密码 |
| **WPA3**（2018） | 新的握手方式（SAE），**密码简单也很难离线暴力破解**；每次连接用新密钥 | AES-CCMP / GCMP | 新设备才支持，部署复杂 |

- 规律：越新越安全，核心是 RC4 → **AES**（呼应 p.11）；WEP 是「算法过时」的经典例子（§10）。
- **Personal vs Enterprise**：Personal 是大家共用一个 Wi-Fi 密码（家里）；Enterprise 是每人用自己的账号登录（802.1X，公司、学校，例如用学校账号登录的 eduroam）——这就是 L3 的 authentication 落到 Wi-Fi 上。

#### ④ Bluetooth：Passkey only

- 第一次连接要**配对**：屏幕显示或要求输入一个配对码（passkey），双方确认一致才连上，之后用对称加密通信。*Passkey only* 指蓝牙主要靠这个配对码保证安全。
- 范围约 **30 英尺（10 米）**内的人都可能尝试连你。常见攻击名（了解即可）：**Bluejacking**（发垃圾消息）、**Bluesnarfing**（偷读通讯录、文件）、**Bluebugging**（控制设备）。
- 课件四条建议：不接受不认识的配对请求、不在公共场所配对、删除不用的连接、不用时关闭。
- ⚠️ 这个 passkey（蓝牙配对码）和 L6 的 **passkey 无密码登录**（设备存私钥、对服务器的 challenge 签名，属于非对称）不是一回事。

**串回主线**：TLS 和 PGP 都是 hybrid（非对称交换钥匙 / 签名，对称加密数据）；协议里只要有「签名」就是非对称，TLS 传输阶段的完整性校验是对称的 MAC；SSL → TLS、WEP → WPA3、MD5 → SHA-256 都是「算法过时就换」。

## 8. 🔴 业务里怎么用（老师强调）✍️

老师说要知道密码学**在业务里怎么组合起来用**。答业务题用一个固定的四步：

<Callout type="exam" title="业务题答题模板">

1. **场景要保护什么**：对照 C / I / A / N 四个目标，先说清楚这个业务最怕什么（被看到？被改？被冒充？事后赖账？）。
2. **选工具**：每个目标对应哪种技术（§6 的表）。
3. **怎么组合**：通常是 hybrid——证书确认身份、非对称交换钥匙、对称加密数据、哈希 / 签名保完整和不可抵赖。
4. **剩下的风险**：密钥管理（被偷、内鬼）、算法过时、易用性（§10）。

</Callout>

| 业务场景 | 最怕什么 | 用到的技术 | 解决的问题 |
|---|---|---|---|
| **网银 / 网购 HTTPS** | 被冒充、被窃听、被改 | 证书（验证网站）+ 非对称（协商会话密钥）+ 对称 AES（传输）+ 哈希（完整性） | A + C + I |
| **电子合同 / 交易确认** | 事后赖账、被改 | 哈希 + 发送方私钥签名 + 证书 | I + A + **N** |
| **软件更新 / 安装包签名**（PKI 实操 1） | 被换成恶意程序 | 厂商用私钥签，用户用证书验证 | A + I（SolarWinds 的教训：签名本身也可能被滥用，构建过程也要保护） |
| **密码存储** | 数据库被偷后密码泄露 | 加盐哈希 | 拿不到明文密码 |
| **数据库 / 备份加密** | 硬盘或备份被偷 | 对称 AES + 密钥管理 | C（PCI DSS 要求） |
| **远程办公** | 公共网络被窃听 | VPN（IPSec / TLS）、SSH | C + I + A（L3 §4） |
| **加密邮件** | 邮件被看、被冒充 | PGP / S/MIME（hybrid + 签名） | C + A + I |
| **Passkey 无密码登录**（L6 开场） | 钓鱼、撞库 | 设备存私钥、服务器存公钥、对随机 challenge 签名、绑定域名 | 防重放、服务器被攻破也没密码可偷、防钓鱼 |
| **区块链** | 账本被改、交易被否认 | 每块存上一块的哈希 + 每个参与者用 PKI 签交易 | I + A + N（**不提供 C**） |

## 9. 🟡 Blockchain（p.30–34）📝🔍

<Figure src="images/page_33.png" caption="每个 Block 保存上一个 Block 的哈希（Prev Hash），串成哈希链" source="Slide 33" />

**课件原文**

> Blockchain is a **peer-to-peer, distributed ledger** that is **cryptographically-secure, append-only, immutable** (extremely hard to change), and **updateable only via consensus** or agreement among peers.

- Peer-to-peer：no central controller，不需要银行或 VISA 这类第三方
- Distributed ledger：each peer holds **a copy of the complete ledger**
- Cryptographically-secure：provides **non-repudiation, data integrity and data origin authentication**
- Satoshi Nakamoto 2008：digital equivalence of cash；fully decentralized（not minted or managed by any central bank）；highly resilient to changes；all transactions perfectly traceable and verifiable；**no single party can shut the system down**
- Transaction integrity：**a chain of inter-related hash values**；hash the entire block of data to produce a summary
- **Cryptography is a MUST**：everyone must use **PKI**, no opt-out；**Bitcoin blockchain is the largest civilian deployment of PKI in the world**

**需要理解：区块链 = 本课工具的组合**

| 区块链的特性 | 靠哪个工具 |
|---|---|
| 改不了（immutable） | **哈希链**：每块存上一块的哈希，改一块后面全断（下面自己试） |
| 知道是谁转的、赖不掉（origin authentication、nonrepudiation） | **数字签名**：每笔交易用转账人的私钥签名 |
| 没有中心、没人能关掉 | **分布式账本 + 共识**：每个节点都有完整副本，改账要说服大多数节点 |

<ChainLab />

- 为什么难改：改了一个旧块，它的哈希就变了，后面每一块的 Prev Hash 都对不上；攻击者要把后面全部重算，还要让大多数节点接受他的版本，而每个节点都有完整副本。
<Figure src="images/page_34.png" caption="Cryptography on Blockchain：每个参与者都必须用 PKI；比特币是全世界最大的民用 PKI 部署" source="Slide 34" />

<QA q="（课件原题 p.34）Is Blockchain provide confidentiality on the financial transactions within the Block?">

**答案：不提供机密性。** 账本对所有节点公开，每个节点都有完整副本，任何人都能看到每笔交易（哪个地址转给哪个地址、多少钱）。区块链提供的是 **integrity**（哈希链）、**data origin authentication** 和 **nonrepudiation**（每笔交易都有转账人的数字签名），也就是 p.31 *cryptographically-secure* 列的三项——里面本来就没有 confidentiality。

*EN:* **No.** The ledger is shared with every peer, so all transactions are visible. Blockchain provides integrity (the hash chain), data origin authentication and nonrepudiation (signed transactions), not confidentiality.

</QA>

## 10. 🟡 风险、挑战与最佳实践（p.36、p.40）📝

<Figure src="images/page_36.png" caption="Strength of Encryption?——Table 10-5 Encryption Key Power：k 位密钥最多要猜 2^k 次；56 位平均 17.1 小时，128 位平均 9.2×10^18 年；Encryption + Key determine the strength (Key more important)" source="Slide 36" />

<Figure src="images/page_40.png" caption="Risk & Challenges：Risks / Challenges / Best Practices / Importance of user education" source="Slide 40" />

> **课件原题（p.36 标题）：** Strength of Encryption?
> **课件答案：** Encryption + Key determine the strength encryption! (Key more important)

**这两页在讲什么**

- **p.36** 用标题提问 *Strength of Encryption?*（加密有多强取决于什么），答案写在下面：**Encryption + Key determine the strength, key more important**。中间那张 **Table 10-5（Encryption Key Power）** 是证据：暴力破解要把所有可能的钥匙试一遍，k 位的钥匙最多有 **2^k** 种。表里每一行就是多一段长度后，要猜多少次、一台电脑要猜多久。
- **p.40** 是全课的收尾：用了加密之后还剩下哪些**风险**、落地时有哪些**挑战**、该怎么做（**最佳实践**），以及别忘了**用户教育**。

**怎么读 Table 10-5**

| 密钥长度 | 最多猜测次数 | 平均破解时间（表里的数字） | 说明 |
|---|---|---|---|
| 16 位 | 65,536 | 0.000000056 秒 | 一眨眼 |
| 56 位 | 7.2 × 10^16 | **17.1 小时** | 老的 DES 就是 56 位，所以被淘汰 |
| 64 位 | 1.8 × 10^19 | 182 天 | |
| 128 位 | 3.4 × 10^38 | **9.2 × 10^18 年** | AES 最短的密钥，宇宙年龄才 1.4 × 10^10 年 |
| 256 位 | 1.16 × 10^77 | 3.1 × 10^57 年 | AES-256 |

- **规律：多 1 位，工作量翻一倍**；从 56 位到 128 位只多了 72 位，时间却从 17 小时变成上亿亿年。
- 「平均」是「最多」的一半：平均猜到一半就中。
- 表的注释说明这是**一台 2020 年的桌面 CPU** 算的；用很多台电脑一起算会快很多，但对 128 位以上仍然没用。量子计算是另一回事（§11）。
- 所以 *key more important*：算法是公开的，强度来自**钥匙够长、够随机、保管得好**。

<KeyStrengthLab />

**课件原文**

- Strength of encryption：**Encryption + Key** determine the strength（**key more important**）
- **Risks**：**key theft**、**insider threats**、**cryptographic algorithm obsolescence**
- **Challenges**：**balancing security and usability**、**system integration**
- **Best practices**：**strong key management**、**layered security**、**regular audits**
- Importance of **user education**

**需要理解：为什么密钥比算法重要**

算法是公开的（AES、RSA 全世界都知道怎么算），安全全靠密钥保密、够长、管得好。钥匙被偷了，算法再强也没用——就像最好的锁，钥匙丢了照样被打开。

| 课件 | 具体是什么 | 例子 / 对策 |
|---|---|---|
| Key theft | 私钥或对称密钥被偷 | 私钥放在专门的硬件里（HSM）、不写进代码；泄露就吊销证书 |
| Insider threats | 有权限的人滥用密钥 | 最小权限、职责分离、审计谁用过密钥（L3 Least Privilege） |
| Algorithm obsolescence | 算法被破或算力进步后不安全 | MD5、SHA-1、WEP 已淘汰；量子计算威胁 RSA（§11） |
| Security vs usability | 太麻烦用户就绕过 | 强制复杂密码 → 用户写在便利贴上；passkey 两者兼顾 |
| System integration | 老系统不支持新算法 | 迁移要盘点所有用到加密的地方 |
| Strong key management | 密钥的一生都要管 | 生成 → 分发 → 存储 → 轮换 → 吊销 / 销毁 |
| Layered security | 不只靠加密 | 加密 + 访问控制 + 监控（L3 Defense in Depth） |
| Regular audits | 定期检查 | 证书快过期了吗？还有人在用弱算法吗？ |
| User education | 人是最弱的一环 | 看到浏览器证书警告不要点「继续访问」 |

## 11. 🟢 量子计算（p.37–39）✍️

<Figure src="images/page_38.png" caption="Quantum Computing – Not a 2036 Problem：金融业量子计算采用率仅 7%；KPMG 的审计问题——做过加密资产盘点吗？知道自己在用哪些算法吗？有 PQC 迁移时间表吗？" source="Slide 38" />

<Figure src="images/page_37.png" caption="Latest Threat：Quantum Computing（BBC 2025 年 2 月）" source="Slide 37" />

> **课件原题（p.37，BBC 文章标题）：** Will quantum computers disrupt critical infrastructure?
> **答案要点：** **有可能，但不知道什么时候。** 今天的基础设施（网银、TLS、证书、数字签名）都依赖 RSA 这类非对称算法；足够强的量子计算机理论上几分钟就能破解，而普通计算机要上百万年。文章强调「我们无法准确预测它什么时候从理论变成现实」，而数字技术无处不在，修起来更复杂——所以现在就要开始准备（下面 KPMG 的审计问题）。

**课件原文**

- Quantum computing uses **qubits** in **superpositions**，可以同时做大量运算
- Today's computers would take **thousands, even millions of years** to crack RSA; a suitably powerful quantum computer could do it **in minutes**
- **Quantum Computing – Not a 2036 Problem**（KPMG）：Audit considerations：cryptographic asset inventory？which encryption algorithms do you rely on？timeline for PQC migration？what products / services might quantum impact？
- Quantum Resilience & **PQC**（Post-Quantum Cryptography，HKIB / IBM）

**需要理解**

- 威胁的是 §3 那个「反方向极难」的数学问题：量子计算机能很快地把大数分解，RSA、ECC 这类非对称算法首当其冲 → 证书、TLS 握手、数字签名都会受影响。
- **为什么现在就要做**：对手可以**现在偷、以后解**（Harvest now, decrypt later）——今天截获加密数据存起来，等量子计算机成熟再解密。需要保密很多年的数据（病历、国家机密、长期合同）已经有风险。
- 现在能做的：**盘点**自己在哪里用了哪些算法（KPMG 的第一个问题）→ 规划 **PQC 迁移**时间表 → 系统设计成能换算法（crypto agility）。
- 这是 §10「cryptographic algorithm obsolescence」的具体例子。

<Callout type="extra" title="对称加密受的影响小得多（课件没讲）">

量子计算对 AES 这类对称算法的威胁有限，把密钥加长（AES-256）就能应对；真正要换掉的是 RSA、ECC 这类非对称算法。

</Callout>

## 12. 本课综合题（长题练习）

<QA q="A customer logs into an online bank. Walk through how symmetric encryption, asymmetric encryption, hashing, digital signatures and certificates each contribute to making the session secure.（15 marks）">

**English**

1. The bank's server presents a **digital certificate** issued by a CA, containing the bank's public key and the CA's signature.
2. The browser verifies the CA's **digital signature** with a trusted root CA key and checks the validity period and domain — confirming it is the real bank.
3. The two sides use **asymmetric** cryptography (RSA / ECDH) to agree a session key that eavesdroppers cannot obtain.
4. Login details and transactions are then encrypted with **symmetric** AES and the session key — fast enough for the whole session.
5. **Hash**-based integrity checks on every record reveal any tampering.
6. The bank stores passwords only as **salted hashes**.
7. Signed transaction confirmations provide **nonrepudiation**.
Each tool covers one property, and PKI combines them into trust that scales.

**中文解析**

① 浏览器连接时，银行服务器发出由 CA 签发的**数字证书**，证书里有银行的公钥和 CA 的签名；② 浏览器用信任的根 CA 公钥验证证书签名（**数字签名**），并检查有效期和域名，确认对方确实是银行；③ 双方用**非对称**算法（RSA / ECDH）协商出一把会话密钥，窃听者无法得到；④ 之后的登录信息和交易数据都用**对称** AES 和会话密钥加密，速度快；⑤ 每条数据附带基于**哈希**的完整性校验，篡改会被发现；⑥ 银行存密码时只存加盐哈希；⑦ 交易确认可用签名提供不可抵赖。结论：每种工具各管一项，PKI 把它们组合成可规模化的信任。

</QA>

<QA q="A company wants to replace paper contracts with an online e-contract platform. Recommend the cryptographic controls it needs and explain what each achieves, including the remaining risks.（12 marks）">

**English**

1. **What must be protected**: contracts must not be altered (integrity), signers must be who they claim (authentication), nobody can later deny signing (nonrepudiation), and contract contents stay private (confidentiality).
2. **Hash + digital signature**: each signer's software hashes the contract and signs the digest with the signer's **private key**; any later change breaks verification, and only the signer could have produced the signature.
3. **Digital certificates from a trusted CA** bind each signer's public key to their verified identity, so a forged key pair is rejected; revocation handles leaked keys or departed staff.
4. **TLS (hybrid)** protects contracts in transit; stored contracts are encrypted with **AES**.
5. **Remaining risks**: private key theft or insider misuse (use hardware key storage, least privilege, audit), algorithm obsolescence and quantum risk for long-lived contracts (plan PQC migration), and usability (signing must stay simple enough that users do not bypass it).

**中文解析**

① **要保护什么**：合同不能被改（I）、签署人身份真实（A）、签了不能赖（N）、内容保密（C）。② **哈希 + 数字签名**：对合同算摘要，用签署人**私钥**签名；之后任何改动都会让验证失败，且只有本人签得出。③ **CA 签发的数字证书**把每个签署人的公钥和核实过的身份绑定，伪造的密钥对会被拒；私钥泄露或员工离职时吊销证书。④ 传输用 **TLS**（hybrid），存储用 **AES** 加密。⑤ **剩余风险**：私钥被偷或内部滥用（硬件存储私钥、最小权限、审计）；合同要保存多年，有算法过时和量子风险（规划 PQC 迁移）；易用性（签署流程要简单，否则用户会绕过）。

</QA>
