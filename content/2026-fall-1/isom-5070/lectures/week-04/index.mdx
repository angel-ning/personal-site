## 0. 核心地图（先建立整体框架）

Week 3 学的 FAIR 给了一个**模型**（Risk = LEF × LM）；这周要做的是把这个模型**用在一整套财务建模流程里**，并且学会**把算出来的数字讲给管理层听**：

```
把技术暴露翻译成财务语言（不是要一个精确数字，是要一条「损失分布」）
   → ① 定义 3–5 个业务场景（不是泛泛的"网络风险"）
      → ② 估计 Loss Event Frequency = TEF × Vulnerability
         → ③ 分组件建 Loss Magnitude（每类损失分开算，可审计）
            → ④ 算控制措施的财务价值：Expected Benefit / Net Benefit / ROI
               → ⑤ 把保险当作一层财务缓冲来建模（不是风险分析的替代品）
                  → ⑥ 记录每个输入的来源、置信度、责任人
                     → ⑦ 把结果组织成一份「30 秒能听懂建议」的高管汇报
```

**一句话抓住本周**：好的财务模型**产出一条损失分布，而不是一个红/黄/绿的分数**——这样管理层才能问"我们预期年损失是多少？""P95 需要备多少资本？""花 1200 万做韧性项目值不值？"这种可以拿来做预算决策的问题。

## 1. 🔴 为什么要做财务建模

> 财务建模是把**技术性的暴露**——比如勒索软件、云攻陷、支付欺诈、第三方中断——翻译成**决策级的财务损失估计**。目标不是预测一个精确数字，而是估计一条**站得住脚的损失分布**、超过关键损失阈值的概率，以及控制措施、保险、韧性投资的经济价值。

🔴 **考点**：NIST 框架帮助围绕威胁事件、漏洞、可能性、不利影响和不确定性做风险评估；**FAIR 提供了把这些组件转成财务场景的定量结构**——两者是互补关系，不是二选一。

```
Annual Loss = Loss Event Frequency × Loss Magnitude
```

🎯 一个实用的模型应该产出**损失分布**，而不只是红/黄/绿评分。这样管理层才能问："我们的预期年损失是多少？"、"P95 需要准备多少资本？"、"一个 1200 万的韧性项目能不能把损失降到足以证明自己划算？"

## 2. 🔴 财务模型的结构（p.5–8）

### 2.1 五个步骤

1. **定义业务场景**：从一个可管理的集合开始——通常 **3–5 个场景**，要具体到能估计、重要到能影响决策
2. **估计 loss-event frequency**：`LEF = Threat Event Frequency × Vulnerability`
3. **分组件建 loss magnitude**：每类损失分开建模——**这样结果可审计，也能看清楚控制措施到底在哪个组件上起作用**
4. **建模控制措施的财务价值**（见第 3 节）
5. **建模保险选项**（见第 4 节）

### 2.2 🟡 业务场景示例（p.6，考试可能要求你自己写一个类似的）

| Scenario | 涉及资产/流程 | 主要风险驱动因素 | 典型损失机制 |
|---|---|---|---|
| 勒索软件中断核心交易或客户服务系统 | 交易、运营、客户门户 | 加密、勒索、恢复失败 | 收入损失、员工加班、事件响应、修复、客户补偿 |
| BEC（商业邮件诈骗）导致欺诈性付款 | 财务、资金部、客户开户 | 社会工程、付款验证薄弱 | 直接现金损失、调查、法律成本 |
| 第三方市场数据/云/SaaS 中断 | 交易工作流、投资组合运营 | 供应商韧性失效 | 生产力损失、错过交易、合同救济、声誉损害 |
| 客户或员工数据泄露 | CRM、HR、投资者记录 | 错误配置、凭证盗窃、供应商访问 | 取证、通知、法律咨询、监管行动、索赔 |
| 特权访问被攻破 | 生产环境、源代码、支付 | 身份薄弱、权限过大 | 中断、欺诈、恢复、监管与诉讼暴露 |

<Callout type="tip">

这张表其实就是 Week 3 §2 威胁建模五要素的"场景 + 资产 + 驱动因素 + 损失机制"简化版——**先挑场景，才谈得上后面估计 LEF 和 LM**。

</Callout>

### 2.3 🔴 估计 Loss Event Frequency（p.7）

```
LEF = Threat Event Frequency (TEF) × Vulnerability
```

- **TEF**：相关威胁**对该资产采取行动**的频率有多高
- **Vulnerability**：威胁行动**真正成功、变成损失事件**的概率

| Input | Low | Most likely | High | 可能的证据 |
|---|---|---|---|---|
| 每年相关的钓鱼/凭证攻击次数 | 100 | 300 | 800 | 邮件遥测、SOC 工单、威胁情报 |
| 单次攻击活动造成重大攻陷的概率 | 0.2% | 0.7% | 2.0% | 紫队测试、控制测试、历史事件 |
| 由此得出的年化损失事件数 | 0.2 | 2.1 | 16.0 | 模型推导输出 |

### 2.4 🔴 分组件建 Loss Magnitude（p.8）

> 分开建模每一类损失，**结果才可审计，也能看清楚控制措施到底在哪个组件上起作用**。

| 损失组件 | 典型计算方式 | 例子 |
|---|---|---|
| Incident response and forensics | 外部时薪/日薪 × 时长 + 内部投入 | 取证公司、违约律师、危机公关 |
| Restoration and replacement | 系统重建、数据恢复、软硬件、加班 | 身份、端点、服务器、应用的恢复 |
| Business interruption | 损失的边际贡献 + 生产力损失 + 合同罚款 | 交易停摆、无法处理申购/赎回 |
| Fraud or theft | 总损失 − 追回 − 保险自留 | 欺诈电汇或勒索相关成本 |
| Regulatory and legal | 按司法辖区、记录、事实和律师意见给出区间 | 调查、通知、抗辩、和解 |
| Customer and counterparty remediation | 服务信用、补偿、监控、账户补救 | 客户影响成本 |
| Reputation and secondary effects | 保守、有证据支撑的区间 | 客户流失、融资延迟、获客成本上升 |

<Callout type="warn">

这七个组件本质上就是 Week 3 FAIR 案例里 Primary/Secondary Loss 的**更细粒度拆解**——面试/考试如果要你"分组件建 LM"，直接套用这张表的分类，不要笼统地写"损失很大"。

</Callout>

## 3. 🔴 控制措施的财务价值（p.9）

> 一项控制投资在经济上是否合理，取决于它**预期的损失降低量加上其他可衡量的收益，是否超过它的全生命周期成本**。

### 3.1 控制措施降低风险的三种方式

1. **Reduce Frequency（降低频率）**：抗钓鱼 MFA、特权访问管理、EDR、缩小攻击面
2. **Reduce Severity（降低严重度）**：不可篡改备份、分段环境、事件响应保留服务、经过测试的灾难恢复
3. **Transfer/recovery improvement（转移/恢复能力提升）**：保险、合同赔偿、欺诈追回流程

### 3.2 🔴 三个核心公式（必背）

```
Expected Benefit = Baseline Expected Loss − Residual Expected Loss
Net Benefit = Expected Benefit − Control Lifecycle Cost
ROI = (Expected Benefit − Control Cost) / Control Cost
```

## 4. 🔴 保险建模（p.10）

> 保险应该被建模成**一层财务缓冲**，而不是风险分析的替代品。

```
Net Retained Loss = Gross Covered Loss − min(max(Gross Covered Loss − Retention, 0), Limit)
                     + Uncovered Loss + Premium
```

<Callout type="tip">

拆开看：`min(max(Gross Covered Loss − Retention, 0), Limit)` 就是**保险公司实际赔付的钱（Insurance Recovery）**——先减掉自留额（Retention，低于这个数保险公司不赔），再封顶在 Limit（保单上限）。公司自己扛下来的 Net Retained Loss = 覆盖内损失 − 保险赔付 + 除外责任损失（Uncovered）+ 保费本身（Premium，这笔钱不管有没有出险都要付）。

</Callout>

### 🔴 保单要考虑的条款（p.10，🟡 列举题）

➢ Per-claim retention or deductible（单次索赔自留额/免赔额）
➢ Policy limit 与 aggregate limit（保单限额与累计限额）
➢ 针对勒索软件、营业中断、支付欺诈、监管抗辩、事件响应的**sub-limit（子限额）**
➢ 营业中断保障的等待期
➢ 除外责任：战争、系统性事件、未加密数据、控制不足除外
➢ 交易对手与保险公司的信用质量
➢ **潜在相关性**：一次大范围的云或身份提供商中断可能**同时**影响多个被保险方（保险公司的赔付能力可能被摊薄）

## 5. 🟡 数据质量：每个输入都要能说清楚来源（p.11）

> 一个好的网络财务模型应该为每一个重大输入记录**来源、置信度、责任人和刷新日期**。

要清楚区分并记录：

- **Known data**：内部记录里已知的数据
- **External benchmarks**：作为代理指标的外部基准
- **Expert judgments**：专家判断及其置信度
- **Assumptions**：需要验证的假设
- **Correlations**：可能显著推高尾部损失的相关性

| 输入类别 | 证据来源 |
|---|---|
| 资产与流程关键性 | Business-impact analysis、RTO/RPO、流程图、收入与成本数据 |
| 事件频率 | SOC 案例、钓鱼遥测、既往事件、同业情报、红队结果 |
| 控制有效性 | 审计证据、渗透测试、桌面演练结果、恢复测试、控制覆盖率 |
| 停机成本 | 财务模型、交易/运营数据、工资、服务水平承诺 |
| 响应/恢复成本 | 既往发票、供应商价目表、采购合同、IR 保留服务条款 |
| 法律与监管成本 | 隐私法律顾问、合规、监管映射、实际索赔历史 |
| 保险追回 | 保单条款、经纪人分析、理赔经验 |

<Callout type="memo">

这张表和 Week 3 §7.6"怎么把损失分成 6 类再算 LM"是同一套精神的延伸：**每个数字背后都要能指出"这是从哪来的"**，而不是凭感觉估一个数——这也是 FAIR/财务建模能说服高管和审计的原因。

</Callout>

## 6. 🔴 Executive Presentation（高管汇报）

### 6.1 面向执行层的一页仪表盘该有什么（p.12）

> 最有用的仪表盘通常**只有一页**：最高风险场景、预期年损失、P95 损失、风险胃口阈值、保险追回、最大损失驱动因素，以及排名前 1–3 的投资建议的风险降低经济性。

对金融机构而言，投资目标是**降低少数几个严重场景**的概率和财务影响：账户接管与欺诈、勒索软件导致的运营中断、第三方集中失效、数据泄露、特权访问滥用。

| 原则 | 实践中的意思 | 对投资的含义 |
|---|---|---|
| **保护关键业务服务** | 从交易、支付、客户报告、投资者门户、数据和监管运营出发，而不是泛泛的 IT 资产 | 在停机、篡改或数据丢失会造成重大财务/监管损害的系统上多花钱 |
| **降低尾部风险** | 关注可能造成严重 P95/P99 损失的事件，而不只是频繁的低价值告警 | 优先恢复能力、身份、分段、危机响应、供应商韧性 |
| **衡量风险降低** | 把每项投资和 loss-event frequency 或 loss magnitude 的降低挂钩 | 重大支出要求量化的 baseline 和剩余风险案例 |
| **建韧性，不只是预防** | 假设控制措施有时会失效 | 为备份隔离、恢复测试、响应保留服务、沟通、人工替代方案拨款 |
| **避免控制蔓延** | 整合度差的工具堆栈会造成成本、告警过载和盲区 | 整合重叠工具；优先投资覆盖面、集成和运营成熟度 |

### 6.2 🔴 汇报技巧（p.13，最容易考"弱开场 vs 好开场"对比）

**❖ 开场就给一句话的建议和要求的决策**：

| | 内容 |
|---|---|
| ❌ **弱开场** | "过去一年，安全团队完成了跨 12 个领域的评估，识别出 57 个发现项" |
| ✅ **好开场** | "批准一个 1000 万美元、18 个月的韧性项目。它解决了造成 70% 建模严重损失暴露的两个场景——身份攻陷和第三方中断——预期能把年化损失暴露降低 2500–4000 万美元。" |

🔴 **踩坑提醒**：弱开场的问题不是"没有信息量"，而是**信息量全给了过程（做了什么），没有给结论（该做什么决定）**——高管要的是"建议 + 决策要求"，不是工作汇报。

**❖ 让业务影响变得明确**，每个要点都要能挂上这些商业词汇：

- **Growth 增长**：收入增长、客户留存、市场扩张、新能力
- **Cost 成本**：申请的预算、运营成本降低、回本周期
- **Risk 风险**：损失暴露、监管影响、韧性、风险降低
- **Strategy 战略**：竞争地位、战略一致性、可选性
- **Execution 执行**：时间线、依赖关系、责任人、治理
- **Return 回报**：ROI、NPV、避免的损失、可衡量的结果

**❖ 每页标题就是结论**：好标题让听众"扫一眼就懂"，不需要读细节。

### 6.3 🔴 Executive Presentation 的八段结构（p.14）

> 好的高管汇报**不是一份报告**，而是**一个决策工具**：先给答案，再用少量事实支撑，让权衡取舍清晰可见，最后以一个高管可以批准/拒绝/修改的精确行动结尾。

1. **Decision and recommendation**：说明诉求、建议、所需资源、预期结果
2. **Why**：背景——触发事件、市场机会、风险变化、监管、客户需求或战略紧迫性
3. **Current position and material gap**：展示少量关键事实，量化暴露
4. **Options and trade-offs**：比较现实的选项——什么都不做、最低合规选项、推荐选项、加速选项
5. **Recommended path and economics**：解释为什么推荐这个选项，给出成本、收益、避免的损失、上行空间和关键假设
6. **Execution, risks, and governance**：高层计划/里程碑、依赖关系、责任人、主要剩余风险和缓解措施
7. **The specific ask and next steps**：重复清楚需要什么批准或指示、什么时候要、谁接下来行动
8. **Appendix**：其余所有支撑材料，以防被追问

### 6.4 🟡 高管汇报自查清单（p.15）

- 看完第一页 30 秒内，别人能不能复述出你的建议？
- 要求的决策是否明确（金额、范围、责任人、截止日期）？
- 有没有同时展示上行和下行——包括"什么都不做"的代价？
- 假设、不确定性和风险是否被承认，而不是被藏起来？
- 选项和权衡是否可见？
- 单看每页标题，能不能拼出一个连贯的故事？
- 细节有没有移到附录？
- 有没有为最可能被追问的问题准备好简洁的回答？
- 结尾那页有没有让下一步行动**清清楚楚**？

<Callout type="exam">

**一句话记住整节课**：如果老板听完要问"你到底需要我做什么？"，说明这份汇报没有把 ask 讲清楚——这既是 Executive Presentation 的自查标准，也是本周 Preliminary Presentation 该照着做的模板。

</Callout>

## 🔴 综合缩写速查表

| 缩写 / 公式 | 含义 |
|---|---|
| `Annual Loss = LEF × LM` | 财务建模的核心公式，承接 Week 3 的 FAIR |
| `Expected Benefit = Baseline − Residual` | 一项控制措施带来的风险降低金额 |
| `Net Benefit = Expected Benefit − Cost` | 扣掉成本后的净收益 |
| `ROI = (Expected Benefit − Cost) / Cost` | 每一块钱成本换回多少净收益 |
| `Net Retained Loss = Gross − Recovery + Uncovered + Premium` | 公司在保险之后自己实际扛下的损失 |
| P95 / P99 | 第 95 / 99 百分位损失，衡量尾部风险 |
| RTO / RPO | Recovery Time / Point Objective，恢复时间/恢复点目标 |

## 模拟自测题

<QA q="财务建模的目标是什么？为什么说「产出一个红/黄/绿评分」不够好？">

财务建模的目标不是预测一个精确数字，而是产出一条**站得住脚的损失分布**、超过关键阈值的概率，以及控制措施/保险/韧性投资的经济价值。红/黄/绿评分只能告诉你"高中低"，回答不了"我们预期年损失是多少"、"P95 要备多少资本"、"这笔投资值不值"这些管理层真正需要拿来做预算决策的问题。

</QA>

<QA q="给定 Baseline expected loss = US$6M，Residual expected loss = US$2.2M，Control cost = US$3M（比 Week 3 的案例更贵）。这项控制措施在经济上还值得投资吗？">

Expected Benefit = 6 − 2.2 = US\$3.8M
Net Benefit = 3.8 − 3 = **US\$0.8M**（仍然 > 0）
ROI = (3.8 − 3) / 3 ≈ **27%**

Net Benefit 仍为正，所以经济上依然值得投资，只是比 Week 3 原案例（Cost=US\$2.2M 时 Net Benefit=US\$1.6M）的净收益薄了不少。可以用本笔记 §3.2 的 ControlRoiCalculator 互动验证。

</QA>

<QA q="一次损失事件的 Gross Covered Loss = US$8M，保单 Retention = US$1M，Limit = US$4M，另有 Uncovered Loss = US$0.5M，Premium = US$0.2M。计算 Insurance Recovery 和 Net Retained Loss。">

Insurance Recovery = min(max(8 − 1, 0), 4) = min(7, 4) = **US\$4M**（触顶了 Limit）
Net Retained Loss = 8 − 4 + 0.5 + 0.2 = **US\$4.7M**

公司自己实际扛下来的钱（US\$4.7M）比 Gross Covered Loss（US\$8M）少，但**远不是零**——超过 Limit 的部分（8−1−4=3M 里保险不赔的那部分）、Uncovered Loss 和 Premium 都要自己承担。可以用本笔记 §4 的 InsuranceCalculator 互动验证。

</QA>

<QA q="对比 p.13 给出的「弱开场」和「好开场」例子，说明为什么弱开场是无效的，好开场做对了什么。">

弱开场（"过去一年完成了跨 12 个领域的评估，识别出 57 个发现项"）的问题是：它只汇报了**做了什么工作**，没有给出**建议或需要的决策**——高管听完不知道自己该批准什么。好开场（"批准一个 1000 万美元、18 个月的韧性项目……预期降低 2500–4000 万美元年化损失暴露"）在第一句话里就给出了：① 明确的建议和金额，② 针对的具体场景（身份攻陷、第三方中断），③ 量化的预期收益——符合"先给答案，再用事实支撑"的高管汇报原则。

</QA>

<QA q="Executive Presentation 的八段结构里，Options and trade-offs 这一步通常要比较哪几类选项？">

现实的选项通常包括：什么都不做（do nothing）、最低合规选项（minimum-compliance option）、推荐选项（recommended option），以及可能的加速选项（accelerated option）。展示"什么都不做"的代价尤其重要——它是后面证明推荐方案economics合理性的对照基准。

</QA>
