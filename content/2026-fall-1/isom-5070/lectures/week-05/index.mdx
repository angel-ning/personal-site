## 0. 核心地图（先建立整体框架）

这节课把"风险管理"的视角从"自己公司内部"扩展到**别人的系统会不会连累自己**——供应商和 AI 系统本质上都是"**外部引入、但风险要自己扛**"的同一类问题：

```
为什么要管第三方（NIST CSF Govern.GV.SC 明确要求）
   → 供应商风险的生命周期（Intake → … → Offboarding，8 个阶段）
      → 怎么给供应商分级（Tiering 公式，决定尽职调查做多深）
         → 尽职调查该问什么、要什么证据（11 个领域）
            → 该写进合同的控制要求（baseline / higher-tier / 合同条款）
               → 合作期间持续监控 + 治理角色分工 + 报告指标
                  → AI 系统是「一种特殊的、越来越常见的第三方/内部依赖」
                     → 用 NIST AI RMF（Govern-Map-Measure-Manage）管住它
                        → AI 同时给企业自己引入了 6 类新风险
```

**一句话抓住本周**：Vendor Risk Management 和 AI Risk Management 用的是**同一套底层逻辑**——先按风险大小分级（Tiering），再按级别决定要多深的尽职调查和多严的控制，最后持续监控、定期重评估。学会了 Week 5 的 Vendor 生命周期，NIST AI RMF 的四个功能（Govern/Map/Measure/Manage）其实就是同一个思路换了一套术语。

## 1. 🔴 为什么要单独管第三方风险

> NIST CSF 2.0 把这件事明确放在 **Govern 功能的 GV.SC 类别**下，要求组织：按关键性给供应商排优先级、把安全要求写进合同、签约前做尽职调查、在合作关系存续期间持续监控供应商风险、把相关供应商纳入事件响应、并为终止合作做规划。

🎯 **考点**：这句话直接呼应 Week 2 学过的 **NIST CSF 六大 Functions**——供应商风险不是一个孤立话题，它就挂在 **Govern（GV）**这个 Function 下面的一个具体 Category（GV.SC = Supply Chain）。如果考试问"第三方风险管理在 NIST CSF 里属于哪个 Function"，答案是 **Govern**，不是 Identify 或 Protect。

企业应该建立一个 **Cyber VRM（Vendor Risk Management）项目**，目的是：
1. 识别哪些外部方会影响你的 **机密性、完整性、可用性、韧性或监管义务**（即 Week 1 学过的 CIA + 韧性 + 合规）
2. 施加**成比例的**技术和合同控制（不是所有供应商都用同一套严格程度）
3. 持续监控重大变化

## 2. 🔴 Vendor Risk Management 生命周期（p.4，8 个阶段）

| Lifecycle stage | Cybersecurity objective | Key control activities |
|---|---|---|
| **Intake and classification** 准入与分类 | 在接触供应商前先搞清楚暴露面 | 识别服务关键性、数据类型、连接方式、访问级别、托管模式、地理位置、分包商、可替代性 |
| **Inherent-risk assessment** 固有风险评估 | 决定要做多深的尽职调查 | 给数据、访问、关键性、交易量、监管影响、集中度、第四方依赖、可恢复性打分（见第 4 节公式） |
| **Pre-contract due diligence** 签约前尽职调查 | 验证供应商的控制环境 | 审查 SOC 报告、ISO 27001 证书、渗透测试摘要、漏洞管理证据、事件响应计划、BCP/DR 证据、数据安全架构与政策 |
| **Risk treatment** 风险处置 | 降低超出胃口的风险 | 要求整改、收窄访问权限、加补偿性控制、隔离数据、用加密/密钥控制、改集成设计，或拒绝/更换供应商 |
| **Contracting and onboarding** 签约与准入 | 把要求转化为可执行的技术/合同保障 | 安全附录、事件通知条款、访问控制、数据处理条款、审计权、分包商承诺、安全集成审查 |
| **Continuous monitoring** 持续监控 | 发现安全态势下滑或新的外部暴露 | 安全评级、威胁情报、泄露监控、控制证明刷新、漏洞/补丁报告、SLA 与事件回顾 |
| **Incident and resilience** 事件与韧性 | 在供应商被攻陷或不可用时限制损失 | 联合应急手册、桌面演练、证据保全、升级路径、BCP/DR 测试、替代服务/人工应急方案 |
| **Offboarding** 下线退出 | 消除剩余的网络暴露 | 禁用账号/令牌、吊销证书和 API key、移除网络路由、验证数据归还/销毁、保留所需日志与证据 |

<Callout type="memo">

这 8 个阶段和 Week 3 的七步法结构相通：**Intake+Inherent-risk = 建立上下文/评估固有风险，Due diligence+Treatment = 评估控制/选处置，Contracting = 落地，Monitoring+Incident = 监控/测试/重评估，Offboarding 是 Vendor 场景特有的"退出"步骤**（内部风险管理没有这一步，但供应商关系有始有终）。

</Callout>

## 3. 🔴 给一个供应商建档的七个步骤（Onboarding，p.5）

1. **登记供应商和服务**：记录负责人、合同价值、支持的业务服务、数据类别、访问类型、托管地点、集成方式、重要分包商
2. **判断关键性和固有网络风险**：**先分级、再收集证据**——支付处理商、云服务商、托管服务商（MSP）、身份提供商、订单管理平台、或有生产环境管理员权限的供应商，通常需要更高级别的审查
3. **执行相应的尽职调查路径**：低层级供应商做基础筛查；Tier 1 供应商要做完整评估，必要时还包括架构、隐私、财务韧性、第四方审查
4. **记录剩余风险、选择处置方式**：批准 / 有条件批准（要求整改） / 加补偿性控制 / 由指定权限人接受风险 / 推迟上线 / 换供应商
5. **落实必要的合同条款**：在必要的网络安全条款到位之前，**不允许**生产使用、共享敏感数据、给予特权访问或做关键集成
6. **在合作期间持续监控**：定期重新评估，并在泄露、重大中断、所有权变更、服务扩张、新数据用途、新分包商或安全评级显著恶化时做事件驱动的复查
7. **为事件和退出做规划**：在关系变得关键之前，就准备好联系人、通知与取证配合要求、恢复义务、替代方案、数据导出能力和下线流程

<Callout type="tip">

**先分级、再决定审查深度**是这一节最重要的一句话——不是所有供应商都做同样严格的尽职调查，这也是第 4 节 Tiering 公式存在的意义：**用一个数字决定该走哪条尽职调查路径**。

</Callout>

## 4. 🔴 Vendor Tiering：怎么给供应商打分（p.6）

供应商的固有网络风险分级应该基于以下**六个因子**的**加权评分**：

| 因子 | 权重 | 1 — Low | 3 — Moderate | 5 — High/Critical |
|---|---|---|---|---|
| **D**ata exposure 数据暴露 | 0.25 | 公开信息或无公司数据 | 内部/机密数据 | 客户 PII、凭证、支付数据、**MNPI**、监管数据、密钥 |
| **A**ccess & connectivity 访问与连接 | 0.25 | 无访问；独立服务 | SSO 或有限用户访问 | 特权/admin 访问、API 写权限、生产网络连接、端点 agent |
| **C**riticality 业务关键性 | 0.20 | 容易替换的非核心工具 | 重要的支撑性工作流 | 关键业务服务：交易/事务工作流、身份、云、支付、安全运营 |
| **B**last radius 影响半径 | 0.15 | 用户少；环境隔离 | 部门级影响 | 全企业级或面向客户的中断；系统性运营影响 |
| **F**ourth-party 第四方暴露 | 0.10 | 无实质性分包商 | 已知的托管/分包商，范围有限 | 依赖云、MSP、软件库、离岸交付、或不透明的分包商 |
| **R**egulatory 监管影响 | 0.05 | 影响很小 | 涉及合同/审计要求 | 金融服务外包、隐私泄露、市场行为、记录留存或监管报告相关 |

🔴 **必背公式**：

```
Vendor Inherent Cyber Risk Rating = 0.25D + 0.25A + 0.20C + 0.15B + 0.10F + 0.05R
```

🎯 **考点**：权重 **D 和 A 并列最高（各 0.25）**，说明"数据有多敏感"和"能拿到多大的访问权限"是判断供应商风险的两个最主要维度；**R（监管影响）权重最低（0.05）**——不是不重要，而是监管影响往往是数据/访问/关键性风险实现之后的**下游后果**，不是独立的一等风险来源。

<Callout type="extra" title="课外补充：MNPI 是什么">

**MNPI = Material Non-Public Information（重大非公开信息）**，金融行业合规里的常用词，指**还没有对外公开、一旦公开会显著影响证券价格**的信息（比如未发布的财报、并购计划、评级变动）。掌握 MNPI 的人如果据此交易或泄露给他人交易，构成**内幕交易 (insider trading)**——这是证券监管的核心红线。老师的背景是 Morgan Stanley 的交易风控主管，MNPI 会被单独列进"高敏感数据"一档（和客户 PII、支付数据同级），就是因为供应商一旦接触到这类信息，泄露或滥用的**监管和法律后果比一般数据泄露严重得多**。

</Callout>

> Slide 原例：**rating 超过 3.5** 的供应商应该是 **Tier 1**。一个带 SSO、员工数据有限的 SaaS 报销工具可能是 Tier 3；一个云端订单管理系统、或做威胁检测响应的托管服务商（MSP MDR）通常应该是 Tier 1。

<Callout type="warn" title="权重和 3.5 这个门槛不是行业统一标准">

这套 **0.25/0.25/0.20/0.15/0.10/0.05 的权重分配，以及「rating > 3.5 → Tier 1」这个门槛，都是这份 slide/该机构自己校准的例子，不是放之四海而皆准的规定**。不同企业会根据自己的风险胃口、供应商结构和历史数据，调整每个因子的权重、要不要加新因子、把门槛设在哪——例如一家对数据泄露特别敏感的机构可能把 D 的权重进一步提高到 0.35；一家供应商数量少但都很关键的企业可能把 Tier 1 门槛降到 3.0，让更多供应商接受完整审查。**记公式的结构（哪几个因子、大致的权重排序）比记住具体数字更重要。**

</Callout>

## 5. 🟡 安全尽职调查该问什么（p.7，11 个领域）

这张表**结构高度统一**：每个领域都是"该问的问题 + 该要的证据"，理解这个模式比逐字背更重要。

| Domain | 该问的问题（精简） | 该要的证据（精简） |
|---|---|---|
| **Governance** 治理 | 安全是否对高管负责？有没有正式 ISMS？ | 安全政策集、治理架构图、风险登记摘录、ISO 27001 证书与 SoA |
| **Identity and access** 身份与访问 | 是否强制 MFA？特权访问怎么管？ | IAM 标准、MFA 覆盖率、PAM 架构、季度访问审查证据 |
| **Data security** 数据安全 | 数据在哪被谁处理？传输/静态是否加密？谁管密钥？ | 数据流图、数据清单、加密标准、密钥管理设计、留存/删除流程 |
| **Cloud and infrastructure** 云与基础设施 | 云租户、生产环境、网络、密钥、配置怎么保护？ | 架构图、云安全基线、分段设计、配置合规报告 |
| **Application security** 应用安全 | 代码、依赖、API、发布怎么保护？ | Secure-SDLC 政策、SAST/DAST 结果、软件物料清单（SBOM）、代码审查/发布控制 |
| **Vulnerability management** 漏洞管理 | 关键漏洞多快被发现和修复？ | 扫描覆盖率、补丁 SLA、修复账龄报告、外部测试摘要 |
| **Logging and detection** 日志与检测 | 能不能检测、调查、留存攻击证据？ | SIEM/SOC 描述、日志范围、留存周期、威胁检测与升级流程 |
| **Incident response** 事件响应 | 出事后怎么通知和支持你？ | IR 计划、近期桌面演练证据、升级联系人、通知流程、取证支持能力 |
| **Resilience** 韧性 | 勒索软件/云故障/区域中断后能不能恢复？ | BCP/DR 计划、RTO/RPO 承诺、恢复测试报告、备份架构与不可篡改控制 |
| **Personnel security** 人员安全 | 员工是否经过背调、培训、按角色限权？例如有没有做刑事记录、信用记录、**药物滥用（drug screening）**这类背景筛查？ | 背调政策、安全培训指标、入职/调岗/离职流程 |
| **Subprocessors** 分包商 | 谁是重要的第四方，怎么被治理？ | 当前分包商清单、地点、条款下沉、第四方评估方法 |

<Callout type="extra">

还有两个补充领域没列进表但同样重要：**Privacy and compliance**（能否满足数据保护和行业监管义务，要 DPA、隐私影响评估、跨境传输机制）和 **Secure exit**（数据、集成、凭证能不能安全移除，要退出手册、数据可携带流程、销毁证明模板）。

</Callout>

## 6. 🔴 控制基线：Baseline vs Higher-Tier（p.8–9）

### 6.1 所有能接触公司数据的供应商都要满足的 Data Security Baseline

➢ 对所有管理和远程访问强制 MFA
➢ 用现代 TLS 加密传输中的公司数据，静态数据也要加密
➢ 维护有文档记录的漏洞管理项目和明确的修复时限
➢ 运行有指定升级联系人的事件响应流程
➢ 在合同规定的时限内，通知确认或合理怀疑影响你数据/服务的安全事件
➢ 维护安全的下线流程，及时移除用户和管理员访问权限
➢ 披露重要分包商，并从其处取得适当的合同承诺
➢ 在服务对运营重要时，维护备份和经过测试的连续性流程

### 6.2 🔴 Higher-Tier（Tier 1）供应商需要额外满足的控制

➢ 特权账号在可行时用**抗钓鱼 MFA**，加一套 PAM 流程
➢ 隔离的生产环境、最小权限、强密钥管理、有文档记录的管理访问日志
➢ 集中式安全日志、明确的留存期、7×24 检测或有文档记录的监控模型、及时升级重大告警
➢ **至少每年一次**独立渗透测试，并跟踪重大发现直至闭环
➢ 关键的互联网暴露漏洞要在**短且合同明确的期限内**修复，例外情况要有补偿性控制
➢ 经测试的勒索软件恢复能力；受保护、访问受控、在合适情况下不可篡改的备份
➢ 每年针对约定的 RTO/RPO 目标做 BCP/DR 测试，测试结果可按要求提供
➢ 当前的分包商清单，以及对重大变更的批准/通知权
➢ 经测试的事件响应演练，包括客户通知、遏制、恢复、沟通、取证保全
➢ 强健的退出策略，包括数据导出、过渡协助、凭证吊销、销毁证明、备用服务方案

<Callout type="memo">

**Baseline 是"能碰数据就必须做到"的底线，Higher-tier 是"Tier 1 才需要"的加强版**——两者的很多条目其实是同一个主题的"基础版 vs 强化版"：MFA → 抗钓鱼 MFA；漏洞管理 → 渗透测试+短期限修复；备份 → 不可篡改备份+年度 DR 测试。

</Callout>

## 7. 🔴 该写进合同的条款（p.10）

| 条款 | 要点 |
|---|---|
| **Security standard** 安全标准 | 供应商要维持与服务和风险相称的安全控制，参照你的政策、ISO 27001、SOC、NIST CSF 或其他约定基线 |
| **Incident notification** 事件通知 | 明确触发条件、渠道、**首次通知的截止时间**、更新频率、所需信息、事后报告义务——**不能只写"promptly"这种模糊词** |
| **Audit and evidence rights** 审计与证据权 | 定义获取 SOC 报告、认证、测试摘要、修复状态的权利；对关键供应商，要能做相应比例的审计或评估 |
| **Sub-contractor governance** 分包商治理 | 要求披露、安全尽职调查、条款下沉、对重大新分包商的通知或同意 |
| **Vulnerability & remediation obligations** 漏洞与修复义务 | 定义严重度方法论、修复期望、例外处理、补偿性控制 |
| **Data ownership and handling** 数据归属与处理 | 定义允许的处理方式、访问限制、加密、留存、存放地点、传输、归还、认证销毁 |
| **Resilience commitments** 韧性承诺 | 合同化的 RTO、可用性目标、DR 测试期望、重大中断报告 |
| **Secure development** 安全开发 | 针对软件供应商，要求 SDLC、依赖管理、安全测试、重大漏洞披露、安全更新实践 |
| **Exit assistance** 退出协助 | 要求配合、数据可携带、迁移支持、连续性承诺、终止后移除访问权限 |
| **Liability and insurance** 责任与保险 | 让责任上限、赔偿条款、网络保险要求与该服务可能造成的损失严重度相匹配 |

🔴 **踩坑提醒**：Incident notification 条款那句"不能只写 promptly"是老师原话强调的点——**合同语言含糊 = 出事时没有可执行的时间线**，考试如果问"这份合同的事件通知条款有什么问题"，答案往往就是"触发条件/时限/所需信息不够具体"。

## 8. 🔴 持续监控（p.11，四种节奏）

| # | 类型 | 频率 | 内容 |
|---|---|---|---|
| 1 | **Operational Oversight** 运营监督 | 每季度 | SLA 表现、中断、安全事件、未结的整改计划、用户/访问变更、客户投诉 |
| 2 | **Control Assurance** 控制保证 | 每半年或每年 | 更新的 SOC 报告、ISO 证书、渗透测试摘要、BCP/DR 测试、政策/控制变更、分包商变更 |
| 3 | **External Threat Monitoring & Response** 外部威胁监控 | 持续 | 暴露的服务、泄露的凭证、域名仿冒、勒索/敲诈报告、安全评级变化、已披露漏洞、泄露报告 |
| 4 | **Reassess** 重评估 | 每年或有重大变化时 | 见下方触发条件 |

### 🔴 Reassess 的触发条件

➢ 供应商开始处理更敏感的数据类别，或获得了特权访问
➢ 服务变得对面向客户、受监管、支付、交易、身份或安全运营场景至关重要
➢ 发生重大事件、长时间中断、勒索软件事件或控制失效
➢ 供应商变更所有权、托管商、运营地域、关键分包商或核心技术栈
➢ 出现影响持续经营能力的重大不利财务事件
➢ 合同续约、大幅扩展，或转向新的部署模式

<Callout type="tip">

这四种监控节奏和第 8 节的触发条件，和 **Week 3 的 Monitor/Test/Report/Reassess** 是同一套逻辑在"第三方"场景下的具体化——**Operational + External Threat 对应 Monitor，Control Assurance 对应 Test（周期性拿证据验证），Reassess 触发条件几乎和 Week 3 的十条一一对应**。

</Callout>

## 9. 🔴 治理：谁该对什么负责（p.12）

| 角色 | 负责什么 |
|---|---|
| **Board / risk committee** 董事会/风险委员会 | 网络风险胃口、重大风险例外、关键集中度暴露、项目有效性 |
| **Executive sponsor / CISO** | C-SCRM 政策、安全要求、风险方法论、监控标准、报告 |
| **Business/vendor owner** 业务/供应商负责人 | 业务需求、服务关键性、准入信息的事实准确性、运营表现、整改责任 |

| **Information security** 信息安全 | 固有风险挑战、控制评估、技术架构审查、修复验证、事件协调 |

| **Legal/privacy/compliance** 法务/隐私/合规 | 合同条款、数据处理义务、监管要求、违规通知、审计权、记录留存 |

<Callout type="exam">

</Callout>

## 11. 🔴 NIST AI RMF：AI 系统的可信度特征（p.14）

> NIST AI Risk Management Framework（AI RMF）旨在为组织提供一个**通用操作模型**，用来识别、评估、优先排序和处理影响个人、企业、社会和环境的 AI 风险。NIST AI RMF 主要围绕 **trustworthiness（可信度）** 来评估 AI 系统风险。

| 特征 | 实践中要问的问题 |
|---|---|
| **Valid and reliable** 有效可靠 | 系统对其预期用途和使用人群，表现是否准确、一致？ |
| **Safe** 安全 | 可预见的误用、失效或意外影响，会不会造成物理、财务、运营或人身伤害？ |
| **Secure and resilient** 安全且有韧性 | 能否抵御攻击、操纵、中断、模型窃取、数据投毒、prompt injection 和性能退化？ |
| **Accountable and transparent** 可问责且透明 | 归属、决策权、文档、可追溯性、升级路径是否清晰？ |
| **Explainable and interpretable** 可解释 | 相关干系人能否理解输出到足以验证、质疑或恰当使用的程度？ |
| **Privacy-enhanced** 隐私增强 | 个人和敏感数据是否被最小化、保护、治理，并符合法律和组织义务？ |
| **Fair, with harmful bias managed** 公平、管理有害偏见 | 组织是否测试过跨相关人群/使用场景的表现差异或有害结果？ |

<Callout type="tip">

这七个特征里，**Secure and resilient** 那一条（model theft、data poisoning、prompt injection）和第 15 节"AI Impacts on Cyber Security"的新风险几乎是**同一批词汇**——说明 AI RMF 的"安全"维度和这门课其他几周讲的网络安全风险管理是**同一套语言**，不是另起炉灶。

</Callout>

## 12. 🔴 NIST AI RMF 的四个功能（p.15，必背）

AI RMF 被组织成四个功能：

```
① Govern the program（治理这个项目）
   → ② Map what could go wrong and for whom（画出可能哪里出错、对谁）
      → ③ Measure the exposure with evidence（用证据衡量暴露程度）
         → ④ Manage residual risk through decisions, controls, monitoring, remediation（管理剩余风险）
```

| Function | Objective | 典型的金融行业证据 |
|---|---|---|
| **Govern** | 为 AI 风险建立文化、政策、问责制、角色和监督 | AI 政策、风险胃口、模型清单、指定的业务/技术/风险/法务/合规负责人、审批委员会、员工培训、问题升级与事件流程 |
| **Map** | 定义 AI 系统、其上下文、预期用途、干系人、影响、假设和风险 | 用例评估、数据流图、客户影响分析、供应商/模型依赖图、禁止用途分析、model card、human-in-the-loop 设计 |
| **Measure** | 用合适的定性和定量方法分析和监控 AI 风险 | 准确度与校准测试、公平性测试、红队测试、对抗性与安全测试、幻觉/依据性评估、隐私测试、漂移指标、独立验证 |
| **Manage** | 对剩余风险排优先级、响应、记录并持续监控 | 控制计划、接受标准、部署门槛、补偿性控制、人工复核阈值、模型回滚/kill switch、KRI、事件响应、定期重新验证 |

<Callout type="memo">

**Govern 定文化和问责（谁说了算），Map 画风险地图（哪里可能出错、对谁），Measure 拿证据量化（暴露有多大），Manage 处理剩余风险（怎么办）**——这和 Week 3 七步法的"① 建立治理 → 威胁建模 → 评估风险 → 处置 → 监控"结构几乎是一一对应的，只是换了一套 AI 专属的术语和证据类型。

</Callout>

## 13. 🟡 NIST AI RMF 怎么落地（p.16，7 步）

1. 建立完整的 AI 清单，**包括嵌在 SaaS 工具里、从外部采购的 AI 功能**（很容易被忽略）
2. 按影响给每个用例分级——例如低风险的生产力辅助，vs 面向客户的决策、金融犯罪控制、信贷、招聘、监控或交易
3. 对中高影响用例，要求**部署前的 AI 风险评估**
4. 按分级定义最低证据要求：文档、数据控制、安全测试、验证、偏见测试、人工监督、审批要求
5. 把 AI 风险接入企业现有的风险分类体系和问题管理流程（**不要另起一套体系**）
6. 设定可衡量的部署与监控阈值——例如准确度、幻觉率、差异化影响、事件、override 率、漂移、安全测试指标
7. 对模型变更、供应商变更、重大 prompt/工作流变更和新出现的威胁，实施持续治理

| **NIST AI RMF 1.0** | 基础框架：可信 AI 概念、风险框架、成果声明 | 建立 AI 治理和风险管理的操作模型 |
| **AI RMF Playbook** | 映射到每个 RMF 子类别的建议行动 | 把 RMF 的成果转化为政策、流程、测试、证据、控制活动 |
| **NIST AI 600-1** | Generative AI Profile：GenAI 专属风险与落地指南 | 针对 LLM、RAG 系统、copilot、agent、基础模型用例定制 RMF 落地方式 |
| **AI RMF crosswalks/resources** | 与其他标准的映射与配套材料 | 把 AI RMF 和 ISO、隐私、网络安全、模型风险、企业风险项目整合起来 |

## 14. 🔴 AI Impacts on Cyber Security：采用 AI 新增的六类风险（p.18）

> 部署 AI 会扩大组织**自己的攻击面**，因为它需要把企业数据、模型、应用和基础设施集成在一起。

| # | 风险 | 说明 |
|---|---|---|
| 1 | **Data leakage 数据泄露** | 敏感的 prompt、文档、源代码、客户数据或凭证，可能通过未经批准的工具、薄弱的数据处理或权限过大的集成而暴露 |
| 2 | **Prompt injection** | 不可信的内容可以操纵 AI 系统泄露信息、绕过预设指令，或采取不安全的行动 |
| 3 | **Model and supply-chain compromise 模型与供应链攻陷** | 包括被投毒的训练数据、被攻陷的模型或软件包、恶意插件、不安全的 API、依赖项漏洞 |
| 4 | **Excessive agent privileges 代理权限过大** | 一个连接了邮件、云存储、源代码管理、工单系统或生产系统的 AI agent，能把一次模型错误或 prompt injection 变成一次实质性的安全事件 |
| 5 | **Shadow AI 影子 AI** | 员工使用未经批准的工具，造成可见性、数据治理、隐私和留存方面的缺口 |
| 6 | **Overreliance and automation bias 过度依赖与自动化偏见** | 一个看起来很可信的模型输出，可能导致分析师或操作人员接受错误结论、忽略对抗性操纵，或采取有害行动 |

<Callout type="exam">

🎯 **考点**：这六类风险和第 11 节的可信度特征、第 12 节的 Measure/Manage 功能是**同一个问题的三个角度**——例如"Prompt injection"对应可信度里的 "Secure and resilient"，该用 AI RMF 的 **Measure**（对抗性与安全测试）去发现它，用 **Manage**（人工复核阈值、kill switch）去兜底。如果考试给一个 AI 场景问"这属于哪类风险、该用 AI RMF 哪个功能应对"，按这个对应关系答题。

**记忆锚点**：④ Excessive agent privileges 尤其值得多想一层——它不是一个新的攻击手法，而是**把 Week 3 讲过的"权限过大 (excessive permissions)"这个老问题，套在了 AI agent 这个新执行体上**；本质仍然是最小权限原则（least privilege）没有落实。

</Callout>

## 模拟自测题

<QA q="第三方/供应商风险管理在 NIST CSF 2.0 里属于哪个 Function 的哪个 Category？为什么不是 Identify 或 Protect？">

属于 **Govern（GV）** 功能下的 **GV.SC（Supply Chain）** 类别。因为供应商风险管理的核心是"定政策、定问责、定优先级、监督"——按关键性给供应商排优先级、把安全要求写进合同、指定谁负责签字批准，这些都是治理层面的决策，而不是具体去盘点资产（Identify）或落实具体防护措施（Protect）。Govern 是"谁说了算、方向是什么"，供应商风险管理首先要解决的正是这个问题。

</QA>

<QA q="一个供应商的评分是：D=5, A=3, C=5, B=3, F=1, R=3。用 slide 默认的权重（0.25/0.25/0.20/0.15/0.10/0.05）和默认门槛（3.5）算出它的 rating，并判断是不是 Tier 1。">

Rating = 0.25×5 + 0.25×3 + 0.20×5 + 0.15×3 + 0.10×1 + 0.05×3
= 1.25 + 0.75 + 1.0 + 0.45 + 0.10 + 0.15
= **3.70**

3.70 > 3.5，所以这个供应商**是 Tier 1**，需要走完整评估路径（证据审查，必要时还要做架构、隐私、财务韧性、第四方审查）。可以用本笔记第 4 节的 VendorTierCalculator 互动验证——记得这里用的权重和 3.5 门槛是 slide 的默认校准，换一套权重或门槛，同样的 D/A/C/B/F/R 打分可能得出不同的分级结论。

</QA>

<QA q="Baseline controls 和 Higher-tier controls 的区别是什么？请各举两个例子说明「基础版 vs 强化版」的对应关系。">

Baseline 是**所有能接触公司数据的供应商**都必须满足的底线要求；Higher-tier 是**Tier 1 供应商**才需要额外满足的加强版要求。对应关系例如：① MFA（baseline，强制所有管理/远程访问）→ 抗钓鱼 MFA + PAM 流程（higher-tier，专门针对特权账号）；② 有文档记录的漏洞管理项目和修复时限（baseline）→ 每年独立渗透测试 + 关键漏洞短期限修复（higher-tier）；③ 备份和经测试的连续性流程（baseline）→ 经测试的勒索软件恢复能力 + 不可篡改备份 + 年度 BCP/DR 测试对齐 RTO/RPO（higher-tier）。

</QA>

<QA q="NIST AI RMF 的四个功能分别是什么？请把它们和 Week 3 七步法的阶段对应起来。">

Govern（治理项目）→ 对应七步法的 ① Establish context and governance；Map（画出可能哪里出错、对谁）→ 对应 ② Identify assets 和 ③ Threat Modeling；Measure（用证据衡量暴露）→ 对应 ④ Assess inherent risk（以及借助 Week 3/4 的 FAIR 定量化）；Manage（管理剩余风险：决策、控制、监控、修复）→ 对应 ⑤ Select and implement risk treatment、⑥ Assess residual risk、⑦ Monitor, report, test, reassess。四个 AI RMF 功能本质上是把七步法压缩成了四个更粗的阶段，术语不同但底层逻辑一致。

</QA>

<QA q="列举「企业采用 AI 后新增的六类风险」，并说明 Excessive agent privileges 这一条和 Week 3 学过的什么概念是同一个本质问题。">

六类风险：① Data leakage 数据泄露；② Prompt injection；③ Model and supply-chain compromise 模型与供应链攻陷；④ Excessive agent privileges 代理权限过大；⑤ Shadow AI 影子 AI；⑥ Overreliance and automation bias 过度依赖与自动化偏见。

Excessive agent privileges 的本质是 **least privilege（最小权限原则）没有落实**——一个连接了邮件、云存储、源代码管理、生产系统的 AI agent，如果权限过大，一次模型错误或 prompt injection 就能被放大成实质性的安全事件。这和 Week 3 威胁建模里"weakness (vulnerability)"这一环节讲的"excessive cloud permissions"是同一类问题，只是攻击/失效的执行体从人类账号换成了 AI agent。
